# Docket

An issue tracker for people and agents, modeled on Linear: workspaces, teams, issues, docs, comments. Web UI for people, MCP for agents. Bun + SQLite + TypeScript, self-hosted anywhere. Everyone signs in; agents are apps with their own tokens.

Rules: Docket copies Linear's features; "nano" is about the implementation. Minimal, simple, clean code, few files. Few dependencies (react, react-dom, marked, zod, @modelcontextprotocol/sdk). No frameworks beyond that.

## Layout

```

src/server/index.ts   Bun.serve: routes, /api, /mcp, /ws, serves the web app, prints the setup code

src/server/paths.ts   XDG Base Directory resolution
src/server/db.ts      bun:sqlite connection, schema, change events, shared validation
src/server/access.ts  accounts, sessions, API keys, one-time codes, workspaces and members; the Actor
src/server/tracker.ts teams, issues, comments, labels, documents, projects (every call acts for an Actor)
src/server/inbox.ts   subscriptions and notifications (the inbox), fanned out from tracker.ts
src/server/webhooks.ts webhooks: the outbox written with each change, the sending loop, target checks, admin routes
src/server/auth.ts    credentials → Actor, guards, rate limit, public setup/sign-in routes
src/server/http.ts    security headers, body cap, rate limit per credential, the built web app
src/server/chat.ts    /api/chat proxy to the docket-chat service
src/server/attachments.ts uploads: stored next to the database, sniffed, served to the workspace's members
src/server/api.ts     REST handlers
src/server/mcp.ts     MCP server + tools
scripts/              seed (dev data), sign-in-link (recovery)
src/web/index.html    HTML entry (Bun HTML import, bundled by Bun)
src/web/*.tsx, *.css  React UI
```

Env vars and the optional XDG config file: see README's Configuration section. Dev: `bun run dev` (uses `./dev.db` unless `DATABASE_PATH` is set, and setup code `DEVEL-SETUP` unless `DOCKET_SETUP_CODE` is set). Tests: `bun test`, black-box over HTTP against a temp database. Prod: `bun run start` (sets `NODE_ENV=production`, so Bun serves bundled assets and never shows its dev error page).

## Access

Linear's model: sign-in is always required, accounts are global, each workspace has its own members and roles, agents are app users with their own token, removing someone is suspending them. Enterprise-only Linear features (SAML/SCIM, audit log, an Owner role) are out of scope.

**Accounts** (`users`): an account is a login, a person (`kind: "person"`) or an agent (`kind: "agent"`), with an optional email for people: contact info, unique across accounts (case-insensitively; 409 on a clash), not yet verified (there's no mail) and never used to find an account. How an account is known belongs to each membership, as in Linear: a `username` (lowercase `a-z 0-9 . _ -`, 2–32 characters, starting with a letter or digit; `me` and `docket` are reserved in every workspace), unique within the workspace among its people and agents (409 `Username "x" is taken in <Workspace>`, naming only that workspace), and a display `name`. The same username can be different people or agents in different workspaces, and one person can go by different ones. A person's **default profile** is the membership they joined most recently (whatever its status); it's used where no workspace is in play: prefilling a join, `/api/me` for a session that names no workspace, and the sign-in-link prompt. An agent account has exactly one membership. **Docket's own account** (`users.system = 1`, `kind: "agent"`) is what Docket's automated changes (Auto-close) are attributed to: made the first time Docket acts, it has no membership, so it's never listed, assigned, delegated to or mentioned, and it's known everywhere as `{ username: "docket", name: "Docket", kind: "agent" }`; it never signs in (nothing issues it a session, key or code; a key works only for a member, and a session naming it is refused). The API names people and agents by username in the workspace at hand; responses carry `UserRef = { username, name, kind }`. No passwords.

**Workspaces** (`workspace_members`): each membership has a username and name (see Accounts; suspended members keep theirs, so history keeps its names) and a role, `admin`, `member` or `agent` (agents work in teams but manage nothing: no teams, members, invites or agents), and may be suspended. Joining asks for your profile there: signed out, a name and username; signed in, your default profile unless you pick another. You see only workspaces where you're an active member; anything in another workspace answers 404, as if it didn't exist. Any person can create a workspace and becomes its admin. Any person in the workspace, member or admin, creates teams and edits a team's name and description, as in Linear by default; agents can't (403). Admins rename the workspace, create invite links, change roles, suspend and reinstate members, and add, re-token and remove agents. No one can sign in as someone else: there's no admin sign-in link or impersonation. The last active admin can't be suspended or demoted (409 "Add another admin first").

**Suspend** (`PATCH …/members/:username { suspended: true }`) ends access to that workspace at once (membership is checked on every request; their sockets reconnect without it), and that workspace's keys die at once: their API keys, agent token and chat keys there are deleted. If it was their last active membership, their sessions and unused sign-in links go too, so reinstating (`suspended: false`) gives a clean account that signs in again (the server's CLI); reinstating never brings deleted keys back. Other workspaces and their keys are never touched, so one workspace's admin can't cut anyone off from the others. Suspending or demoting an admin also deletes the unused invites they made there. They stay listed, greyed, so history keeps their name. Removing an agent is suspending it; a new token reinstates it.

**Credentials.** Secrets are random and stored only as SHA-256 hashes.
- **Session**: the web UI's cookie `docket_session` (32 random bytes as hex; HttpOnly, SameSite=Lax, Secure over HTTPS, 30 days, re-sent while in use). Idle for 30 days (by `last_seen_at`, touched at most once a minute) and it's gone. Account settings list sessions (device, IP, last seen), revoke one, or sign out everywhere else.
- **API key**: `Authorization: Bearer dk_<64 hex>`, for scripts, MCP clients and agents; it acts as its owner. It belongs to one workspace, chosen when it's made (default: the workspace you're in); it acts only there, as in Linear: it sees only that workspace (`/api/me`, `/api/workspaces`, lists, `/ws`), and anything in another is 404. People make their own (named, scope `read` or `write`) and revoke them. A read key gets 403 on anything but GET (REST) and on tools that change something (MCP). An agent's token is an API key it owns, in the agent's workspace.
- **Managing access needs a session**: listing, making or revoking API keys, listing or revoking sessions, making sign-in links and invites, creating a workspace, changing your profile, changing members, adding or re-tokening agents and managing webhooks all answer 403 to an API key. A leaked key can't mint credentials that outlive it, or lock its owner out of their other keys.
- **Webhook secrets** are the one secret kept in the clear: signing a delivery needs it. Shown once (create, rotate), never returned otherwise. See Webhooks.
- **One-time codes**: 10 symbols of `A–Z 2–9` without `I O 0 1` (50 bits), shown as `XXXXX-XXXXX`, single-use, 15 minutes. A link is `<origin>/login#<code>`: the fragment never reaches the server or its logs, and the page removes it from the address bar at once.
  - **Invites** (a workspace and role) are handed over by the admin, not tied to anyone: redeemed while signed in, one adds you to the workspace (as your default profile, or the `name` and `username` you send); signed out, it creates a new account and its membership (name, username, optional email).
  - **Sign-in links** open one person's account and may record a workspace: from yourself (to sign in on another device; it records the workspace you're in), or from the server's shell (`bun run sign-in-link <username> [workspace]`, for when nobody can sign in). The CLI finds the person holding that username (in that workspace, else in any; agents are refused); if several people do, it exits 1 listing `<workspace key> · <name>` for each, so you name the workspace. Redeeming one while signed in as someone else deletes that session first, so the browser is never signed in as two people. Suspension from your last workspace deletes your unused codes.
- **Setup code**: while there are no users, the server prints one at startup (`DOCKET_SETUP_CODE` fixes it, e.g. for tests and dev). `POST /api/setup` with it creates the first person, signed in, as admin of a new workspace. A wrong code is 403; once any user exists, 409.

**Rules for every request** (`auth.ts`): `/api/*` accepts a session cookie or an API key; `/mcp` only an API key; `/ws` either. Cookies ride along on same-site requests (a sibling subdomain, another localhost port), so a cookie-authed WebSocket or non-GET request needs our own `Origin` (403 otherwise), and an invite only joins the signed-in user when it does. No or bad credentials: 401 (a 401 caused by a stale cookie also clears it). Signed in but not allowed (not an admin, read-only key, someone else's comment): 403. Outside your workspaces: 404. **Every data request acts in one workspace**: a key's own, or a session's `X-Docket-Workspace: <key>` (the web app sends the one its URL shows), or, without the header, a session's only active workspace. A key's header naming a different workspace is 404. Teams, issues, labels, documents, trash and the chat proxy all act there: team keys, identifiers and slugs resolve in it, and lists show only it. Naming a workspace you aren't an active member of is 404; a session in several that names none is 400 `Pick a workspace: send X-Docket-Workspace`. Account routes (`/api/me`, sessions, keys, sign-in links, `/api/workspaces…`, `/api/locate`) need no workspace. Request bodies must be `Content-Type: application/json`, compared exactly on the media type before any `;` (so `text/plain;charset=application/json` is refused), else 415: browsers can't send that cross-origin without a CORS preflight, which Docket never allows, so this is the CSRF defence. The one exception is an upload (`POST /api/attachments`), whose body is the file's bytes as `Content-Type: application/octet-stream`, compared the same way: not a CORS-simple type either. Host check (DNS rebinding): `/api/*`, `/mcp` and `/ws` answer 403 unless the `Host` header's hostname (port ignored, case-insensitive) is `localhost`, `127.0.0.1`, `[::1]` or listed in `DOCKET_HOSTS`. Setup and code attempts are rate-limited per client IP: after 10 failures (401/403) in a minute, 429 until the minute ends (behind a proxy, all clients share the proxy's IP). The app shell, manifest, service worker and icons stay public; they hold no data.

**HTTP layer** (`http.ts`): every response carries `Content-Security-Policy` (`default-src 'self'`, plus Google Fonts; `img-src 'self' data:`, so no remote image loads, markdown's included (see Attachments); `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`; no inline script), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and over HTTPS `Strict-Transport-Security`; API answers add `Cache-Control: no-store` (unless the handler set its own: an attachment's) and `Vary: X-Docket-Workspace` (so a cache, like the service worker's offline fallback, never serves one workspace's answer in another). Request bodies over 1 MB answer 413 (uploads: over 10 MB); without a `Content-Length`, Bun cuts a body off at 11 MB. Texts are capped: titles 500 characters, names 200, descriptions and comments 100,000, doc content 500,000 (also after `edits`), else 400. Each credential (API key or session; no credential: the client IP) gets a token bucket of 600 requests refilling at 20 a second across `/api`, `/mcp` and `/ws`; past it, 429 with `Retry-After`. In production the web app is built once at startup and served with these headers; `bun run dev` keeps Bun's hot-reloading server.

**Assistant proxy** (`chat.ts`, when `CHAT_URL` is set; `GET /api/me` says `chat: true`): `/api/chat` and `/api/chat/*` go to `{CHAT_URL}/chat[/*]` (docket-chat's `CHAT_API.md`). Only a browser session gets through (an API key: 403), after the usual Origin, rate-limit and JSON checks; bodies over 16 KB answer 413. The path must stay under `/chat` once resolved (`/api/chat/%2e%2e/x` is a 404, never `{CHAT_URL}/x`). It forwards the method, query, body, `Content-Type`, `Accept` and `Last-Event-ID`, never cookies, and sets `Authorization: Bearer <chat key>`; it sends back the status, `Content-Type`, `Cache-Control`, `Retry-After`, `X-Accel-Buffering` and the body unbuffered (SSE), and aborts upstream when the browser does (Stop). Answers other than JSON or an event stream become 502, so nothing the service sends renders as a page on Docket's origin. The service has 90 s to start answering and 5 minutes in all. Its own errors look like the service's: `{error, code}` (`not_configured` or `not_found` 404, `forbidden` 403, `invalid` 413/415, `chat_unavailable` 502, `timeout` 504). Docket's usual checks answer first, as `{error}` without a code: 401 (no session), 403 (cross-origin), 413 (over 1 MB), 429 (rate limit). Without `CHAT_URL`, 404.

**Chat keys**: a read API key, one per browser session and workspace, for the workspace the chat panel is in (its `X-Docket-Workspace`, never forwarded; before minting, the proxy answers 400 `invalid` when a session in several names none, and 404 `not_found` for a workspace you aren't in). Named "Chat (automatic)", minted by the proxy and kept only hashed (the token lives in the server's memory). It lives 30 minutes (`DOCKET_CHAT_KEY_TTL_MS`) and is reused while it has two thirds of that left, so a forwarded key always has 20 minutes to go. It's deleted with its session (sign-out, revoke, idle expiry) or with suspension from its workspace, and doesn't appear in the key list. One request writes: a `POST /api/chat/actions/:id/confirm` (the person confirming a change the assistant proposed; matched exactly on the resolved path) gets a write chat key minted for it alone, deleted when that answer ends, fails or is stopped, with 5 minutes as a backstop. Every other chat request reads. `GET /api/me` answers `credential: "session" | "key" | "chat"`, so docket-chat can accept only chat keys. Any key past `expires_at` is dead everywhere (401) and purged at startup, hourly and on each mint.

**Stale tabs**: tabs share one cookie, so the web app sends `X-Docket-User: <account id it shows>` (`Me.user.id`) with every request. If it's not the signed-in account (someone signed in as someone else in another tab), the request gets 401 `{ switched: true }` and the tab reloads as whoever is really signed in, instead of acting as them under the old name.

**Workspaces can't be deleted** yet (like projects before them); a person who can sign in can always create one.

**Authors** are never sent by clients: every write is attributed to the signed-in user or agent (Docket's own changes to @docket, on their behalf). Only a comment's author can edit or delete it (403 otherwise, with no admin override).

## Data

Migration 1 creates the schema (`db.ts`); migration 2 adds `deleted_at` to issues and documents (the trash) and a unique index on `lower(users.email)` (older duplicates keep the email on the oldest account); migration 3 adds `expires_at` and `session_id` to API keys (chat keys); migration 4 gives every API key a `workspace`: an agent's token goes to its workspace, a person's existing key to the workspace they joined first, chat keys are dropped (minted again per workspace), and keys whose owner has no active workspace left are deleted; migration 5 moves `username` and `name` from `users` onto every one of that user's `workspace_members` rows (unique per workspace; the role CHECK also allows `guest`), rebuilding both tables with SQLite's 12-step procedure and keeping every id and row; migration 6 makes team keys and doc slugs unique per workspace: teams get an internal `id` (numbered in `created_at, key` order) that issues and documents point to, documents get their `workspace`, and all three tables are rebuilt the same way, keeping every id, identifier, slug and `next_number`; migration 7 adds `issue_activity`, where history starts: every existing issue gets one `created` row, by its creator at its `created_at`; migration 8 adds `mentions`, empty; migration 9 adds `subscriptions` and `notifications` (empty), subscribes existing work the way new work is (issue creators, assignees, delegates and commenters; a doc's first version's author and its commenters), and backfills `mentions` for every existing description, comment, doc and doc comment as its last save would have recorded them (by the text's last author: a description's last editor from `issue_activity`, else the creator; a doc's last version's author; at that save's time; the doc-content end-of-text rule applies; rows already there stay), subscribing whoever they mention. It notifies no one, and saving an old text again announces only mentions it didn't have. Migration 10 adds `webhooks` and `webhook_deliveries`, empty. Migration 11 adds `issue_relations`, empty. Migration 12 adds `issues.due_on` (null for every existing issue) and a partial index on it. Migration 13 adds `parent_id`, `resolved_at` and `resolved_by_id` to `comments` and `document_comments` (existing comments become unresolved thread roots). Migration 14 adds `reactions`, empty. Migration 15 adds `attachments`, empty. Migration 16 adds `workflow_statuses` and `teams.default_status` (`backlog`): every team gets the default workflow, the six statuses teams always had with the same keys plus Duplicate, so every issue keeps its status, icon, group and order; it changes no row, and refuses (rolls back) if an issue's status isn't one of them. Migration 17 adds `teams.auto_close_parent` and `teams.auto_close_children` (0, off, for every team) and `users.system` (0 for every account; Docket's own account appears on first use, not here), and changes no row. Migration 18 adds `labels` and `issue_labels`: every name in `issues.labels`, trashed issues' too, becomes a workspace label (case variants of one name merge into one, named by the smallest variant in byte order: `Bug` over `bug`; colors from `LABEL_COLORS` in turn by id), and every issue gets a row per name, so it shows the same names; it changes no row, and refuses (rolls back) if an issue's labels aren't a JSON array of strings or if any issue would lose a name. Migration 19 adds `issue_aliases`, empty. Migration 20 adds `issues.archived_at` and `teams.auto_archive_days` (both unset for every existing row, so no existing issue is affected). Migration 21 adds `teams.estimate_scale` and `issues.estimate` (null for every team and issue: estimates off, none set) and changes no row. Migration 22 adds `projects`, `project_teams` and `milestones` (empty) and `issues.project_id`, `issues.milestone_id` and `documents.project_id` (null for every existing row: nothing is in a project), and changes no row. A migration is SQL, or a function (migrations 9, 16 and 18: SQL plus a backfill or a check) run in the same transaction. Migrations run with foreign keys off, each in its own transaction, which runs `PRAGMA foreign_key_check` and rolls back (the server doesn't start) if anything dangles; foreign keys are on afterwards. WAL mode on.

- **users**, **workspaces**, **workspace_members**, **sessions**, **api_keys**, **codes**: see Access.
- **teams**: id (internal; the API names teams by key), workspace, key (2–5 uppercase letters, unique within the workspace: `UNIQUE (workspace, key)`), name, description, next_number, default_status (where new issues start: a backlog or unstarted key; `defaultStatus` in the API), auto_close_parent and auto_close_children (0 or 1; `autoCloseParent`, `autoCloseChildren`: see Auto-close), auto_archive_days (`autoArchiveDays`: see Auto-archive), estimate_scale (`estimateScale`: see Estimates), created_at, updated_at.
- **workflow_statuses** (Linear's workflow: each team's own statuses): id, team_id, key, name, category, color, position; `UNIQUE (team_id, key)`, at most one triage status per team. Categories are fixed, in this order: `triage`, `backlog`, `unstarted`, `started`, `completed`, `canceled`; a team's statuses sort by category, then position (`Team.statuses`). The **key** (`a-z 0-9 _`, derived from the name: "In QA" → `in_qa`, a name with no Latin letters → `status_1`) is what issues, filters, history, notifications and webhooks hold, and never changes; the **name** (unique in the team, case-insensitively) and the color (`#rrggbb`, by default the category's: triage `#f76b15`, backlog `#a3a3a3`, unstarted `#8f8f8f`, started `#e8a800`, completed `#5e6ad2`, canceled `#b4b4b4`) can change, and a status moves within its category by position; its category never changes. A new team gets Backlog, Todo, In Progress, In Review, Done, Canceled and **Duplicate** (`duplicate`, canceled): a system status whose name, color and place are fixed and that can't be deleted. **Triage** is on while the team has a triage status (key `triage`, name "Triage" by default): nothing goes there on its own, only an explicit status (the Triage tab's New issue). **Deleting** a status is refused for Duplicate (400), the default status and the last non-Duplicate status of a category other than triage (409), and one that live or trashed issues are in unless `moveTo` names another status of the team (409 `3 issues are In QA: pass moveTo`); with it, those issues move in one transaction, each as its own status change would (history, `completed_at`, notifications, webhooks, change events). Deleting the triage status turns Triage off. Every change publishes `changed("team")`. Only people change a workflow (agents 403), in their workspace (another workspace's team is 404); agents read it from `list_teams`.
- **issues**: id, team_id, number (per-team sequence from `teams.next_number`; never reused after a delete), title, description, status (a key of its team's workflow; every issue's is one, which the delete rules keep true), priority, labels (legacy JSON array of names: unused since migration 18, which moved them to `issue_labels`), assignee_id (a person), delegate_id (an agent), creator_id, parent_id, due_on, estimate, project_id and milestone_id (see Projects), created_at, updated_at, completed_at, archived_at (`archivedAt`: see Auto-archive). Unique (team_id, number).
- **Due date** (`due_on`, `dueOn` in the API; Linear's due date): a calendar date, `YYYY-MM-DD`, no time; null when there's none. It must be a real date (`2026-02-30`, `tomorrow`, `2026-9-1` are 400 `dueOn must be a date like 2026-09-30`); it sorts and compares as text. The due filters use the server's date, SQLite's `date('now')` (UTC; Docket has no per-person time zone): **overdue** is before today and not in a completed or canceled status (finished work is never overdue), **soon** is today through 7 days ahead, **today**, **any** (has one), **none**. The web app colors dates against the browser's own date instead, so what someone sees matches their calendar; near midnight UTC the two can differ by a day.
- **Estimates** (Linear's, opt-in per team): a team's `estimate_scale` is null (off, the default) or one of four five-value scales (`ESTIMATE_VALUES` in types.ts): `exponential` 1, 2, 4, 8, 16; `fibonacci` 1, 2, 3, 5, 8; `linear` 1–5; `tshirt` XS, S, M, L, XL (Linear's base scales, without its extended tiers). An issue's `estimate` is a position 1–5 in its team's scale, not the value, so changing the scale changes how it shows, never what's stored; totals add the values, t-shirt sizes by position (XS 1 … XL 5). Setting `estimate` (null included) on a team with estimates off is 400 `Turn on estimates for this team first`; anything but an integer 1–5 or null is 400. Turning estimates off hides estimates without clearing them: the API answers `estimate: null` while the team's scale is null, and turning them back on (any scale) shows each issue's position again. A moved issue keeps its position, hidden or shown by its new team's setting; an `estimate` sent with a move is the new team's.
- **labels** (Linear's labels): id, workspace, team_id (null: a workspace label, usable on every team's issues; else that team's own, usable only on its issues), parent_id (its group), name, color (`#rrggbb`; new ones take the next of `LABEL_COLORS` by how many the workspace has), is_group, created_at. A **group** holds labels one level deep, is never applied itself, and its labels share its scope; an issue carries at most one label per group. A label's **path** is `Group/Name` in a group, else its name: what issues' `labels` hold, unique in the workspace case-insensitively (so a workspace label and a team label can't share one). New names can't contain `/` (names from before groups keep theirs). Labels outlive their issues: they're managed in settings, and trashed issues keep theirs.
- **issue_labels**: issue_id, label_id (both cascade). An issue's `labels` are its labels' paths, sorted case-insensitively. Writing `labels` (a whole-list replace, names or paths, case-insensitive) resolves each: a label's path; else a bare name of exactly one grouped label usable on the issue (`Bug` for `Type/Bug`; several are 400 `"High" is ambiguous: Effort/High or Impact/High`); else a new workspace label, or with `Group/Name` a new label in that group (the group found, or made as a workspace group). A group is 400 (`Type is a label group: pick one of its labels, e.g. Type/Bug`), another team's own label 400 (`Label "design" belongs to team WEB`), two labels of one group 400 (`Only one label per group: Type/Bug, Type/Feature`); a refused write creates nothing. Agents create labels this way too; only people manage them (Labels, under REST). Bulk `addLabels` with `Group/Name` swaps out the issue's label of that group; `removeLabels` takes a path or a grouped label's name.
- **issue_aliases** (identifiers from before a move; see Moving an issue): team_id, number, issue_id (cascades on purge), created_at; primary key (team_id, number).
- **issue_blocks**: blocker_id, blocked_id. No cycles: setting `blockedBy` fails (400) if the issue itself or any issue it already blocks, directly or through a chain, is among the blockers.
- **issue_relations** (Linear's other two relations): from_id, to_id, kind (`related` or `duplicate`), created_at; primary key (from_id, to_id, kind). **Related** is two-way: one row per pair (lower id first), so `relatedTo` (a whole-list replace, like `blockedBy`) set on either issue shows on both; an issue can't be related to itself (400). **Duplicate** points one way: from_id duplicates to_id (the canonical issue), at most one per issue. Setting `duplicateOf` records it and sets the issue to its team's Duplicate status (`duplicate`, canceled category; the first canceled status if it had none), overriding a `status` sent with it; `null` clears it and leaves the status as it is. The issue itself, or one that already duplicates it directly or through a chain, is refused (400). The canonical issue lists its duplicates as `duplicates`.
- **issue_activity** (an issue's history, Linear's activity feed): id, issue_id (cascades on purge), actor_id, on_behalf_of_id (for changes Docket makes on its own, whose actor is @docket: whose change set them off; `onBehalfOf` in the API, else null), kind, from_value, to_value (JSON), created_at. One row per change, written as the last step of the change's own transaction, so a refused change (400, 409) writes none; the rows of one mutation share its actor and time. Every change is logged, including those right after creation (unlike Linear: this is an audit trail). Kinds and values: `created` (creating also logs `assignee` and `delegate` when set), `team` the identifier before and after a move, `title` and `status` strings, `description` (no values: no diff), `priority` and `estimate` numbers (an estimate's position), `assignee` and `delegate` user ids (shown as `UserRef`s as they're known in the workspace now, so renames carry and suspended members keep their names), `labels` string arrays (paths as they were then: a label renamed or regrouped later still shows its old name there, and renaming logs nothing; deleting a label logs a `labels` change on each issue it came off, by whoever deleted it), `parent` and `duplicateOf` an identifier, `dueOn` a `YYYY-MM-DD` string, `blockedBy` and `relatedTo` identifier arrays, `claimed` the status before and after (status values are keys; the UI shows them by the team's names and icons), `project` a project's slug, `milestone` a milestone's name as it was then (like a label's path; deleting a milestone logs a `milestone` change on each issue it came off, by whoever deleted it), `trashed`, `restored`, `archived` and `unarchived` (no values). An update logs only fields that really changed (labels, blockers and related issues compare as sets); claiming your own started issue again logs nothing. Issues bumped by a relation change get no rows of their own. `kind` has no CHECK, so new kinds need no rebuild.
- **comments** / **document_comments**: id, issue_id / document_id, author_id, body, created_at, edited_at, parent_id (a reply's thread root, in the same table and on the same issue or doc; null for a root), resolved_at and resolved_by_id (roots only). **Threads** (Linear's replies, one level): a reply to a reply joins its root's thread; a parent that isn't a comment on the same issue or doc is 404 `Comment N not found`. Anyone who can comment resolves or reopens a thread, from its root only (a reply is 400 `Resolve a thread from its first comment`); resolving twice changes nothing. A new reply reopens a resolved thread, so a follow-up is never hidden. A root with replies can't be deleted (409 `This comment has replies; edit it instead`), so nobody's replies go with it; replies delete as any comment. Replies notify like any comment (`commented`, or `mentioned`).
- **reactions** (Linear's emoji reactions, on the issue description, a comment or a document comment; not on document bodies): target (`issue:<id>`, `comment:<id>` or `document_comment:<id>`, the same convention as `mentions.source`), user_id, emoji, issue_id / document_id (whichever the target is on; cascades on purge), created_at; primary key (target, user_id, emoji). `PUT`/`DELETE …/reactions/:emoji` (issue description, issue comment, document comment) add or remove your own; idempotent both ways, and at most 20 distinct emoji per target (409 beyond, only when adding a new one). An emoji is validated as a single grapheme with a pictographic or regional-indicator code point (or a keycap), at most 32 UTF-16 units, stored as sent (NFC); anything else is 400 `emoji must be a single emoji, e.g. 👍`. Reactions never bump `updated_at`, log activity, notify anyone or send a webhook event, only `changed("issue" | "document", …)`; deleting a comment deletes its reactions.
- **subscriptions** (who follows an issue or doc, Linear's subscribers): user_id, issue_id or document_id (exactly one; cascades on purge), created_at; unique per user and issue or doc. You're subscribed when you create an issue or doc, claim an issue, are assigned it, have it delegated to you, are @mentioned in its description, content or a comment, or comment on it; unsubscribing sticks until one of those happens again. `PUT`/`DELETE …/subscription` (and MCP `subscribe`) follow or unfollow by hand.
- **notifications** (the inbox): id, user_id (the recipient), workspace, kind, actor_id, issue_id or document_id (cascade on purge), comment_id (in `comments` or `document_comments`; no FK), status, created_at, read_at. Written in the mutation's own transaction, only for active members of the workspace, never for the actor. Kinds: `assigned` (you became the assignee), `delegated` (an issue was delegated to you, an agent), `mentioned` (a new @mention of you in a description, doc content or comment, with the comment if it's in one; editing a text notifies only mentions it didn't have), `commented` (a new comment on something you follow; not to those it mentions, who get `mentioned`), `status` (an issue you follow moved into a completed or canceled status, or into `in_review` where the team has it; marking it a duplicate included; other changes, claims and relations included, notify nobody). Deleting a comment deletes its notifications. Each person keeps their newest 2,000 per workspace; older ones go as new ones arrive.
- **documents**, **document_versions**, **document_refs**: see Documents.
- **projects**, **project_teams**, **milestones**: see Projects.
- **attachments**: see Attachments.
- **webhooks**: id, workspace (cascades), url, label, resource_types (JSON array), secret (in the clear: it signs), enabled, failures (deliveries in a row that failed for good), created_by, created_at, updated_at. See Webhooks.
- **webhook_deliveries** (the outbox and its log): id, webhook_id (cascades), uuid (`Docket-Delivery`), type, action, entity (identifier, slug, comment id or notification id), payload (JSON without `webhookTimestamp`), status (`pending`, `delivered`, `failed`), attempts, next_attempt_at, response_status, error, created_at, last_attempt_at. Kept 7 days.
- **mentions** (who is @mentioned where; the inbox and webhooks act on them): source (`issue:<id>` for a description, `comment:<id>`, `document:<id>` for content, `document_comment:<id>`), user_id, issue_id / document_id (the issue or doc it's in or on; cascades on purge), author_id, created_at; primary key (source, user_id). Recomputed in the same transaction as every save of the text, like doc refs: mentions the text still has stay as they were (same author and time), new ones get the saver and the save's time, dropped ones go; deleting a comment deletes its rows. Not in the API. **Syntax** (`MENTION_PATTERN` in types.ts, shared with the renderer): `@username` (`[a-z0-9][a-z0-9._-]{1,31}`, case-insensitive, not followed by another username character), not preceded by a letter, digit, `_ . @ / + -` (so `bob@example.com` and `https://x.com/@ana` aren't mentions), in prose: never in code (fenced, indented or inline) or link text. If no one holds the whole match, trailing `. _ -` drop one at a time (`Thanks @ana.` mentions ana). It counts only for an active member of the text's own workspace, people and agents; no one mentions themselves (one someone else made stays when they edit the text). In doc content only, a match that ends exactly at the end of the content doesn't count yet (the editor autosaves mid-word: `@al` on its way to `@alice`); `@al ` or more text after it does.

Identifier = `${team key}-${number}`, parsed case-insensitively, resolved in the request's workspace (`BRD-1` can exist in several); an identifier an issue had before it moved team resolves to it too (everywhere one is read: routes, MCP, relation fields, filters, doc refs, `/api/locate`). Parents, blockers, related and duplicate issues and doc refs never cross workspaces (an identifier from another workspace is 404). Any change to an issue or its comments bumps `updated_at`, strictly forward (at least 1 ms past its previous value, even within one millisecond), since it doubles as the version token for `baseUpdatedAt`; `db.ts` keeps that rule in one place per layer (`bumpedAt` in JS, `BUMPED_AT` in SQL), shared with documents. Creating an issue with a parent, blockers, related issues or a canonical issue bumps and publishes them. Moving an issue to or from the trash also bumps and publishes its sub-issues, its parent, the issues it blocked or was blocked by, its related issues, its duplicates and the issue it duplicates; docs that mentioned it get a `document` event. Changing an issue's parent, blockers, related issues or `duplicateOf` likewise bumps and publishes the old and new parent, each blocker or related issue added or removed, and the old and new canonical issue. `completed_at` is set when the status enters the completed or canceled category, cleared when it leaves (a move within them keeps it). New issues start in the team's default status (backlog unless changed). A status is given by key or, failing that, name, case-insensitively, from the issue's own team only (else 400 `Invalid status "x" for BRD. Use one of: …`). List order: status category, then the team's order, then priority (1→4, then 0 last), then `updated_at` desc; page cursors from before per-team statuses are refused (400: start over). `sort=due` instead puts the earliest due date first and issues without one last, then that same order; page cursors carry both orders' keys.

**Moving an issue** (Linear's, within a workspace only: workspaces are a hard boundary, as for docs): `PATCH { team }` (or MCP `update_issue`) moves it to another team of its workspace. It takes that team's next number (`WEB-5`), and its old identifier goes to `issue_aliases`, so old links, bookmarks and mentions keep resolving to it; `previousIdentifiers` (on `IssueSummary`, oldest first) lists them. Numbers are never reused, so an old identifier never names another issue. A team key resolves only in the request's workspace, so another workspace's team, like an unknown one, is 400 `Unknown team "X": an issue moves only to a team of its workspace`; moving to its own team changes nothing. Its **status** carries over by key if the new team has it, else becomes that team's first status of the same category (not Duplicate), else the team's default (Triage into a team without it); a `status` sent with the move is the new team's (400 otherwise, and nothing moves), and `completed_at` follows categories as usual. Its old team's own **labels** come off (workspace labels stay), unless `labels` is sent with the move, resolved in the new team. It keeps everything else: parent, sub-issues, blockers, related and duplicate issues, comments, reactions, subscribers, mentions, attachments, due date and doc refs all point to its row; it keeps its project and milestone, and its new team joins the project (`project_teams`). One mutation, one history line: `team` (old and new identifier), plus `status` and `labels` if they changed; one webhook `update` whose `updatedFrom` has the old `id`, `team` and `number`; no notification of its own (a status change it causes notifies as usual); `changed("issue")` for both the old and the new identifier. Bulk edits don't move issues.

**Auto-close** (Linear's per-team settings, both off by default; people switch them in team settings, `PATCH /api/teams/:key`, or MCP `update_team`). Only an issue's own status change sets it off (a PATCH, bulk edit or MCP `update_issue` that moves it into the completed or canceled category from outside them), never creating, claiming, trashing, deleting a status, or reopening: closing cascades, reopening doesn't. **Sub-issues** (`autoCloseChildren`, the closed issue's team): its live sub-issues not yet completed or canceled move to the same status: the same key in their own team, else that team's first status of the same category that isn't Duplicate (a parent marked Duplicate gives Canceled); ones already closed are left alone. **Parent** (`autoCloseParent`, the parent's team): when every live sub-issue of a live, open parent is completed or canceled, the parent moves to its team's first completed status (never canceled, even if every sub-issue was). Each issue closed this way sets off the same rules in turn, so it cascades down the tree and up the chain of parents. It all happens in the triggering change's transaction; each closed issue gets `completed_at`, a bump, a `changed` event, its own `status` history row by **@docket** with `on_behalf_of_id` the person or agent who made the change, and the usual status notification and webhook `update` with @docket as actor.

**Trash** (Linear's delete): deleting an issue or doc sets `deleted_at` (`deletedAt` in the API). It leaves lists, search, labels' open counts (its labels stay on it and in the label list), team counts, relations (`blockedBy`, `blocks`, `relatedTo`, `duplicateOf`, `duplicates`, sub-issues) and doc refs, but keeps its links, so restoring (`POST …/restore`) puts everything back. Sub-issues of a trashed issue stay, still pointing at it. A trashed item can be read (with `deletedAt`) and restored, nothing else: edits, comments, claims and new relations to it answer 409 or 400. After 30 days in the trash it's deleted for good (with its comments, versions and refs), at startup and whenever something is trashed, restored or the trash is listed. Deleting or restoring twice is 409.

**Auto-archive** (Linear's, a team setting independent of the 30-day trash above): `autoArchiveDays` (null by default: never), set in team settings or `PATCH /api/teams/:key`. For a team with it set, an issue is archived (`archived_at`, `archivedAt` in the API) once it's been completed or canceled for that many days; a sweep does this at startup and after any change that closes an issue (so a team's backlog of already-old closed issues is swept the next time something in that team changes), attributed to **@docket** with no `onBehalfOf` (it's not set off by anyone's own change). Archiving leaves labels, team counts, search, relations and comments untouched: it only changes default-view visibility, the same as trash but longer, opt-in, and never deleting. An archived issue is read-only like a trashed one (edits, comments and claims: 409) until unarchived (`POST …/unarchive`, or by hand), but can still be linked to (parent, blocker, related, duplicate) since, unlike trash, it isn't going away; it's left out of default issue lists but still matches search (`q`) and opens directly by id or identifier. Archiving or unarchiving by a person or agent (`POST …/archive`, `/unarchive`) is attributed to them, logs `archived`/`unarchived`, and works only on a live (non-trashed) issue. Archiving and unarchiving twice is 409.

**Assignee and delegate** (Linear's model): the assignee is a person who owns the issue; the delegate is an agent working on it for them. Each must be an active member of the issue's workspace of the right kind (400 otherwise, e.g. "claude-a is an agent; set it as the delegate"). `me` means the caller, in values and filters.

**Claim** (`POST /api/issues/:id/claim`, MCP `claim_issue`): a person takes the assignee slot, an agent the delegate slot; an issue not started yet (triage, backlog or unstarted category) moves to the team's first started status (`in_progress` by default), one already started keeps its status. One IMMEDIATE transaction reads and writes, so of two claims racing for a free issue exactly one wins. A completed or canceled one is 409 `"<ID> is <status key>"` (`BRD-2 is done`); one whose slot another active member holds is 409 `"<ID> is claimed by <username>"` (a suspended holder doesn't count). Claiming your own again changes nothing. To hand it back, clear the slot and set status todo.

**Issue versions**: `IssuePatch.baseUpdatedAt`: if present and different from the current `updatedAt`, the PATCH (or `update_issue`) answers 409 `{ "error": "Issue changed since you read it" }` and changes nothing; the check and the write share one IMMEDIATE transaction. Comments bump `updatedAt` too, so send it where lost updates happen (description, and the whole-list `labels`, `blockedBy` and `relatedTo`), not for single-field changes like status or priority.

Rescoping (`team`: a key of the workspace, or null) is 409 `Used on 3 issues outside WEB` if an issue (trashed too) of another team carries it; a group takes its labels along. Moving a label into a group is 409 if an issue would then carry two of it. Renaming or regrouping changes the path on every issue carrying it (a group's: its labels'): they're bumped and published, so a stale whole-list write gets `baseUpdatedAt`'s 409, with no history row or webhook event. Deleting is for good, as in Linear: it comes off every issue (trashed too), each logging a `labels` change (history, webhooks); a group with labels is 409 `Move or delete its labels first`. Every change publishes `changed("label")`.

`Issue` and `Document` carry `subscribed` (you, the caller). A `Notification` is `{ id, kind, workspace, actor, issue: { id, title, status } | null, document: { slug, title } | null, comment: { id, excerpt } | null, status, createdAt, readAt }`: the excerpt is the comment's first 200 characters with runs of whitespace as one space, read when listed (an edit shows). A `Comment` is `{ id, author, body, createdAt, editedAt, parent, resolvedAt, resolvedBy, reactions }`: `parent` is its thread's root id (null for a root), `resolvedAt`/`resolvedBy` are set on a resolved root. `Issue.comments` and `Document.comments` stay one flat list by id; clients group by `parent`. Editing a comment sets `editedAt`; deleting is permanent. A `Reaction` is `{ emoji, users }`, `users` (`UserRef[]`) in the order they reacted; `reactions` is ordered by first reaction. `Issue.reactions` are the description's.

## Realtime

`GET /ws` upgrades to a WebSocket that subscribes to the caller's workspaces (a key's: only its own). After every mutation (REST or MCP) the server publishes a `ServerEvent` `{ type: "changed", entity, workspace, id }` (`entity`: `workspace`, `member`, `team`, `issue`, `document`, `label` (`id`: its id), `project` (`id`: its slug) or `inbox`) to that workspace's sockets only. Two go to one person alone, on their sockets in that workspace (a key's socket: only its own): `inbox` (`id`: their username) whenever their notifications change, and `issue`/`document` when they follow or unfollow it. The UI refetches what it's showing (the inbox and its sidebar count only on `inbox` events). Signing out, revoking a session or key, suspension and agent token changes close the affected sockets (code 4401); clients reconnect with what's current.

## Webhooks

Linear's webhooks (`webhooks.ts`): a workspace's changes are POSTed to an HTTP endpoint as they happen, so an agent runtime can start an agent when it's delegated an issue or mentioned instead of polling. Each webhook belongs to one workspace and hears only it; payloads use that workspace's usernames and `/<ws>/…` URLs.

**Who**: workspace admins, in a browser session, like the rest of access (`requireAdminSession`): an API key gets 403, a member 403, anyone outside the workspace 404 (a webhook id of another workspace too). No MCP tools: agents never mint access. Every write publishes `changed("workspace")`.

| GET | /api/workspaces/:key/webhooks/:id/deliveries | | `WebhookDelivery[]`, newest 50 |

`resourceTypes` is a non-empty subset of `Issue`, `Comment`, `Document`, `Notification`. Enabling resets `failures`; disabling fails its queued deliveries ("webhook disabled"). The secret is `dkwh_` + 32 random bytes as hex, returned only by create and rotate.

**Events** (`WebhookPayload`): `{ action, type, workspace, actor, createdAt, data, updatedFrom?, url, webhookId, webhookTimestamp }`. `action` is `create`, `update` or `remove`; `createdAt` when the change happened; `url` the entity in the web app (`DOCKET_URL` or the server's address, plus `/<ws>/issue/KEY-1` or `/<ws>/doc/slug`); `webhookTimestamp` the attempt's time in ms. An update carries `updatedFrom`: the previous values of the fields that changed. One mutation (REST or MCP) sends at most one event per entity; a change that changes nothing sends nothing. `data` by type:
- **Issue**: `IssueSummary & { description, creator }`. Create; update (`updatedFrom` by field: `title`, `description`, `status`, `priority`, `estimate`, `labels`, `assignee`/`delegate` as `UserRef` or null, `parent`, `blockedBy`, `relatedTo`, `duplicateOf`, `dueOn`, `project`, `milestone`; a move gives the old `id`, `team` and `number`; a claim gives the status and the slot it took); `remove` = moved to the trash; restoring is an `update` with `updatedFrom: { deletedAt }`. Issues bumped only by a relation change send nothing.
- **Comment**: `Comment & { issue: identifier | null, document: slug | null }` (a reply carries its `parent`); update carries `updatedFrom: { body, editedAt }` (only when the body changed), or `updatedFrom: { resolvedAt }` when its thread is resolved or reopened (a reply that reopens one sends the root's update first); remove carries the comment as it was.
- **Document**: `DocumentSummary`, never the content (fetch it). Update's `updatedFrom` always has `updatedAt`, plus `title`, `team`, `position`, `project`, `updatedBy` when they changed; a content change shows as `updatedAt` alone. Updates wait 10 s: saves within that window (autosave) merge into the one queued, unattempted delivery for that doc (newest `data` and actor, oldest `updatedFrom`). Any other event of that doc (trash, restore) sends a held update at once, first. Restore is an update with `updatedFrom: { deletedAt }`, sent at once.
- **Notification**: `Notification & { user }`, `action: "create"`, only for notifications whose recipient is an **agent** (people's are never sent). This is the agent trigger: `data.kind` `delegated` (an issue was delegated to it), `mentioned` (with `data.comment` when in a comment), `commented`, `status`.

Within one mutation, the entity's own event is queued before the notifications it causes (an issue's `create` before its `delegated`).

**Delivery**: an outbox. Each event is written as one `pending` delivery per enabled webhook of the workspace that takes its type, in the mutation's own transaction (a refused change sends nothing). A background loop (`startWebhooks`, from `index.ts`) sends what's due, oldest first, up to 4 at a time and one at a time per webhook, so a webhook's deliveries arrive in order; a write schedules a pass right after it commits, a retry at its time, and a 1 s interval catches anything left (after a restart). Each attempt re-checks the target, then `POST`s with a 5 s timeout, never following redirects, headers `Content-Type: application/json`, `User-Agent: Docket-Webhook`, `Docket-Delivery: <uuid>` (the same on every attempt), `Docket-Event: <type>`, `Docket-Timestamp: <ms>`, `Docket-Signature: <hex HMAC-SHA256 of the raw body with the secret>`. **Verify**: compute the HMAC over the raw body bytes and compare in constant time; reject a `webhookTimestamp` more than a minute off (replays). Any 2xx is delivered and resets the webhook's `failures`. Anything else (another status, a redirect, a timeout, a network error, a blocked target) retries after 1 minute, 1 hour and 6 hours; after the 4th attempt the delivery is `failed` and `failures` += 1; at 10 failures in a row the webhook is disabled (`enabled: false`; the UI says "Disabled after 10 failed deliveries") and its queued deliveries fail. Only the status code and a short error are kept (`HTTP 500`, `timeout after 5 s`, `network error: ConnectionRefused`, `blocked: 10.0.0.5 is private`), never response bodies. Deliveries older than 7 days are deleted at startup and hourly.

**Targets** (`checkTarget`), checked on create and update (400 `Webhook URL refused: <why>`) and before every attempt: `https:` only; no user or password in the URL; the host must resolve (`dns.promises.lookup`, all addresses) and **every** address must be public: not IPv4 0/8, 10/8, 100.64/10, 127/8, 169.254/16 (cloud metadata), 172.16/12, 192.0.0/24, 192.168/16, 198.18/15, 224/4, 240/4, nor IPv6 `::/96` (`::`, `::1`, IPv4-compatible), fc00::/7, fe80::/10, ff00::/8; IPv4-mapped (`::ffff:0:0/96`) and NAT64 (`64:ff9b::/96`) addresses are checked as the IPv4 inside. Numeric host forms (`127.1`, `0x7f000001`, `2130706433`) are normalized by the URL parser first. `DOCKET_WEBHOOK_ALLOW_PRIVATE=true` lifts the address rule and allows `http:` too, for agents on the same host or tailnet; set it only when every admin may reach the server's network. Known limit: DNS can answer differently between the check and the connect (rebinding); redirects are never followed, so a public endpoint can't bounce a delivery inward.

## MCP

Streamable HTTP at `/mcp`, stateless (`WebStandardStreamableHTTPServerTransport` from `@modelcontextprotocol/sdk/server/webStandardStreamableHttp.js`, new server+transport per request, JSON responses). Server name `docket-<workspace>`, title `Docket · <Workspace name>`, `websiteUrl` the public origin (`DOCKET_URL`, else the request's). The instructions open with the Docket origin, the workspace and who you are, so an agent with several connections can tell them apart. Needs an API key; tools act as its owner, in the key's workspace (no tool takes a `workspace`; a stray one is ignored); team keys, identifiers and slugs resolve there, and the instructions and `create_team` say keys are unique within this workspace. `tools/list` shows only what the key can use: a read key sees the read tools (`readOnlyHint`); agents don't see team management; only admins of the key's workspace see `update_workspace`. ## Documents

Linear-style docs inside teams. Markdown is the source of truth (agents write via MCP).

- **documents**: id, workspace, team_id, slug (unique within the workspace: `UNIQUE (workspace, slug)`), title, content, position, project_id (see Projects), created_at, updated_at, updated_by_id.
- **document_versions**: id, document_id, title, content, author_id, created_at. A version is written on every title/content change. Autosave-friendly: if the latest version has the same author and was first saved < 10 min ago, overwrite its title and content instead of inserting. Its `created_at` stays the first save's time, so a long session still gets a new version every 10 minutes. The first version (creation) and checkpoints (restores) are never merged into.
- **document_refs**: document_id, issue_id, ord. Recomputed on every content change from `\b[A-Z]{2,5}-\d+\b` matches that resolve to real issues in the doc's workspace, by their current identifier or one they had before a move (first-mention order).
- Slugs are unique within a workspace (two workspaces can each have `plan`) and stable: renaming a doc never changes its slug. A doc can move to another team of the same workspace (it keeps its project). It can be attached to one project of its workspace (`project`, a slug; another workspace's or an unknown one is 400; `null` detaches it) while keeping its team, as every doc has one. Deleting a doc moves it to the trash (see Trash); purging it deletes its versions, refs and comments.
- Search (`q`) matches title and content. Like issue search, it's a literal substring match: `%`, `_` and `\` in the query are escaped, not wildcards.

## Projects

Linear's projects: a body of work toward a goal, in one workspace, spanning one or more of its teams, with a lead, a status, a target date, milestones (its stages), docs and progress. Unlike Linear: statuses are a fixed list, there's no lead team (`teams` is just the set taking part), a project can't be deleted (cancel it; as with workspaces, trash is a follow-up), and progress counts issues, not estimates. Initiatives, project updates, health and roadmaps are out of scope.

- **projects**: id, workspace, slug (unique within the workspace, stable like a doc's: `UNIQUE (workspace, slug)`; derived from the name, deduped, `project-<n>` if nothing Latin is left), name, description (markdown), status (`backlog` by default, `planned`, `in_progress`, `paused`, `completed`, `canceled`: `PROJECT_STATUSES`), lead_id (a person, an active member), target_date (`YYYY-MM-DD`, a real date, else 400 `targetDate must be a date like 2026-09-30`), creator_id, created_at, updated_at (bumped strictly forward on every change: the version token for `baseUpdatedAt`).
- **project_teams**: project_id (cascades), team_id; primary key (project_id, team_id). At least one; each a team of the project's workspace (a key resolves only there, so another workspace's is 400 `Unknown team "X"`). An issue joining the project (created, set, or moved to another team) adds its team, as Linear shares a project across the teams working on it. `teams` in a PATCH replaces the list, but a team with issues in the project (trashed ones too) stays: 409 `3 WEB issues are in this project`.
- **milestones**: id, project_id (cascades), name (unique in the project, case-insensitively: 409), description, target_date, position (ordering; new ones go last), created_at. Renaming one bumps and publishes its issues (no history row); deleting one takes it off its issues (trashed ones too), each logging a `milestone` change.
- **Issues**: `project` (a slug of the issue's workspace, else 400 `Unknown project "x"`) and `milestone` (a name in the issue's project after the change, case-insensitively: 400 `Unknown milestone "x" in <slug>`, or 400 `Set a project first` without one). An issue is in at most one project and one of its milestones. A different project clears the milestone unless the same change names one of the new project's; `project: null` clears both. A new issue with a `parent` and no `project` joins its parent's project and milestone (as sub-issues do in Linear); `project: null` opts out. Joining or leaving bumps only the issue (history `project`/`milestone`, webhook `updatedFrom`) and publishes the issue and the projects it left and joined.
- **Progress** (`progress`, 0–1) over live issues (not trashed; archived ones count): a completed-category issue counts 1, a started-category one ½, canceled-category ones drop out: `(completed + ½ started) / (issues − canceled)`, or 0 when that's 0. `issueCount` counts live issues. The same for each milestone over its issues.
- Everything is in the request's workspace: another workspace's project is 404 and never listed. Any member, person or agent, creates and changes projects and milestones (a read key can't). Every change publishes `changed("project", slug)`; milestone changes don't bump the project's `updated_at` (its description's version), like doc comments.

| Method | Path | Body / query | Returns |
|---|---|---|---|
| GET | /api/projects | `?team&status=a,b` (`team`: projects it takes part in; unknown team or status: 400) | `ProjectSummary[]` `{ slug, workspace, name, status, lead, teams, targetDate, progress, issueCount, createdAt, updatedAt }`, by status (`PROJECT_STATUSES` order), then target date (none last), then name |
| POST | /api/projects | `ProjectInput` `{ teams, name, description?, status?, lead?, targetDate?, slug? }` (an explicit slug taken in the workspace: 409) | 201 `Project`: the summary plus `description`, `creator`, `milestones` (by position, each `{ id, name, description, targetDate, position, progress, issueCount }`) and `docs` (attached, live) |
| GET / PATCH | /api/projects/:slug | `ProjectPatch` `{ name?, description?, status?, lead?, targetDate?, teams?, baseUpdatedAt? }` (`slug`: 400 `A project's slug never changes`; any other field: 400 naming it; a stale `baseUpdatedAt`: 409 `Project changed since you read it`, one IMMEDIATE transaction) | `Project` |
| POST | /api/projects/:slug/milestones | `MilestoneInput` `{ name, description?, targetDate?, position? }` | 201 `Project` |
| PATCH / DELETE | /api/projects/:slug/milestones/:id | `MilestonePatch` (the same fields; others 400) | `Project` (an id of another project: 404) |

There's no DELETE for a project. UI:
- **Projects list** (`/<ws>/projects`, the sidebar's "Projects"; a team's `/<ws>/t/:key/projects`, the projects it takes part in): a search by name and "New project". A row: the status glyph (the status icons: backlog a dashed ring, planned a ring, in progress a half pie, paused a ring in the urgent color, completed a check disc, canceled an x disc), the name, progress ("42%" and a thin bar), the lead's avatar, the target date and the teams. - **New project modal**: name, description, then status, lead, target date and teams (several; the current team by default). `⌘↵` creates it and opens its page.
- **Project page** (`/<ws>/project/:slug`): crumbs "Projects › Name", the inline-editable name, a row of status, lead, target date and teams, "42% · 12 issues", the description (the issue page's editor, saved with `baseUpdatedAt` and the same conflict banner). **Milestones**: rows with the inline-editable name, target date, progress and count, and a menu (Move up, Move down, Delete); "Add milestone" inline; clicking one filters the issues below to it. ## Attachments

Linear's uploads: files (screenshots, logs, reports) attached to a workspace and linked from any markdown (descriptions, comments, docs). Unlike Linear's, they're private to the workspace (served only to its signed-in members), 10 MB each (`MAX_UPLOAD_BYTES`), and only raster images display inline.

- **Storage** (`attachments.ts`): `attachments/<id>` next to the database (`paths.ts` `attachmentsDir()`: `$XDG_DATA_HOME/docket/attachments`, `/app/data/attachments` in Docker), created at startup. `id` is 16 random bytes, base64url (22 characters): the row's key and the file's name. The file is written first (to `<id>.part`, then renamed, so it's whole or absent), then its row; a failed insert removes the file. Files never change. No delete or cleanup yet: an attachment stays after the text linking it is edited or deleted.
- **attachments**: id, workspace (cascades), name, content_type, size, uploader_id, created_at. `Attachment` in the API: `{ id, url, name, contentType, size, uploader, createdAt }`, `url` = `/api/attachments/<id>/<name>` (the name percent-encoded, parentheses too, so it can't end a markdown link).
- **Name**: the uploaded name without `/`, `\`, `"`, control characters or bidi overrides, trimmed, at most 200 characters; empty is `file`.
- **Type**: sniffed from the first bytes, never the client's claim: PNG, JPEG, GIF, WebP (`RIFF….WEBP`) as their image type; `%PDF-` as `application/pdf`; valid UTF-8 without a NUL in the first 8 KB as `text/plain; charset=utf-8`; anything else `application/octet-stream`. So SVG and HTML are text, never rendered.
- **Serving**: only an active member of the file's workspace gets it (a key: only its own workspace), 404 otherwise, 401 signed out. The id is matched against `^[A-Za-z0-9_-]{22}$` and looked up; a path is never built from the URL. The name in the URL is cosmetic. Headers: the stored `Content-Type`; `Content-Disposition: inline` for the four image types, else `attachment`, with `filename="<ASCII fallback>"; filename*=UTF-8''<encoded>`; `Cross-Origin-Resource-Policy: same-origin`; `Cache-Control: private, max-age=31536000, immutable`; plus the usual headers (nosniff, CSP, no framing).
- Uploading notifies no one, logs no activity and sends no webhook event; the text that links a file does, as usual.

| Method | Path | Body / query | Returns |
|---|---|---|---|
| POST | /api/attachments | `?name=<file name>`; the raw bytes, `Content-Type: application/octet-stream` exactly (else 415) | 201 `Attachment`, in the request's workspace (write access: a read key is 403; a cookie needs our Origin). Empty: 400; over 10 MB: 413 |
| GET | /api/attachments/:id/:name | | the file (see Serving) |

MCP: `attach_file` and `get_attachment` (see MCP).

**Backups**: `./backup.sh` snapshots the database, then copies files in `attachments/` that `backups/attachments/` doesn't have yet (they never change, so new ones are enough; never pruned, since the 14 days of snapshots link to them). Snapshot first, files second, so every snapshot's files exist. Restoring is the snapshot as `docket.db` plus `backups/attachments/` as `attachments/`.

## Deploy

The server serves the web app at `/`, `/login`, `/setup`, `/:ws` and `/:ws/*`, and at the paths from before URLs carried the workspace (`/settings/*`, `/t/*`, `/issue/*`, `/docs`, `/doc/*`) so the app can redirect them; `/api/*` and known files win over `/:ws`, and unknown `/icons/*` stay plain 404s.

`Dockerfile` (oven/bun image) + `docker-compose.yml`: volume `./data:/app/data` (the database, `attachments/`, and `backups/`), port `127.0.0.1:7100:7100`, `restart: unless-stopped`. HTTPS and exposure are the operator's choice (reverse proxy, tunnel, VPN). Anything reached by a hostname other than localhost needs that hostname in `DOCKET_HOSTS`, or data routes answer 403. On first start, the setup code is in the container's log (`docker compose logs docket`). Locked out: `docker compose exec docket bun run sign-in-link <username> [workspace]` prints a one-time link (name the workspace if several people hold that username) (set `DOCKET_URL` so it points at the public origin).
