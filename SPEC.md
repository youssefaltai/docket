# Docket

An issue tracker for people and agents, modeled on Linear: workspaces, teams, issues, docs, comments. Web UI for people, MCP for agents. Bun + SQLite + TypeScript, self-hosted anywhere, or on Cloudflare Workers. Everyone signs in; agents are apps with their own tokens.

Rules: Docket copies Linear's features; "nano" is about the implementation. Minimal, simple, clean code, few files. Few dependencies (react, react-dom, marked, zod, @modelcontextprotocol/sdk, tiptap). No frameworks beyond that.

## Access

Linear's model: sign-in is always required, accounts are global, each workspace has its own members and roles, agents are app users with their own token, removing someone is suspending them. Enterprise-only Linear features (SAML/SCIM, audit log, an Owner role) are out of scope.

**Accounts** (`users`): a login, a person (`kind: "person"`) or an agent (`kind: "agent"`). No passwords. A person may have an email: contact info only (unverified, never used to find an account), unique case-insensitively (409). Names belong to memberships: each has a display `name` and a `username` (lowercased, then `^[a-z0-9][a-z0-9._-]{1,31}$`; `me` and `docket` are reserved), unique within the workspace (409 `Username "x" is taken in <workspace name>`). A person's **default profile** is the membership they joined most recently (whatever its status), used where no workspace is in play: prefilling a join, `/api/me` without a workspace, and the sign-in-link prompt. An agent account has exactly one membership. The API names people and agents by username in the request's workspace, as `UserRef = { username, name, kind }`.
- **GitHub's account** (one per workspace, see GitHub) is an agent member marked `WorkspaceMember.integration`: it has no key, can't be delegated to (400 `delegate: github is an integration`), re-tokened, removed or suspended (400), and pickers and @-autocomplete leave it out.
- **Docket's own account** (`users.system = 1`, an agent) signs Docket's automated changes (auto-close, auto-archive, cycle rollover). Made on first use, it has no membership and never signs in (no session, key or code works for it), and it shows everywhere as `{ username: "docket", name: "Docket", kind: "agent" }`.

**Workspaces** (`workspace_members`): each membership has a username and name (see Accounts; suspended members keep theirs, so history keeps its names) and a role, `admin`, `member`, `guest` (see Teams and guests) or `agent` (agents work in teams and create and configure them, but manage no members, invites or agents), and may be suspended. Joining asks for your profile there: signed out, a name and username; signed in, your default profile unless you pick another. You see only workspaces where you're an active member; anything in another workspace answers 404, as if it didn't exist. Any person can create a workspace and becomes its admin. Any person but a guest, and any agent, creates teams and edits a team's settings. Admins rename the workspace, create invite links, change roles, suspend and reinstate members, and add, re-token and remove agents. The last active admin can't be suspended or demoted (409 "Add another admin first").

**Teams and guests** (Linear's team membership, private teams and Guest role): `team_members` says who is in which team. **One visibility rule** (`SEES_TEAM` in `access.ts`): you see a team of the request's workspace if you're in it, or, unless you're a guest, if it's public. Admins are no exception. Everything team-scoped goes through it (lists, counts, search, filters, labels and their `open` counts, templates, cycles, trash, lookups, `/api/locate`, relations, doc refs, history, the inbox, attachments, `/ws`, MCP), and what you don't see answers like another workspace's: 404 by key, identifier, slug or id; 400 `Unknown team` in a filter, an issue move or a project's teams. Docket's own sweeps and webhooks see everything.

| Action | Who |
|---|---|
| See a public team | everyone in the workspace but guests who aren't in it |
| See a private team | its members (admins list every team's key, name and member count to find one to join: `GET /api/workspaces/:key/teams`) |
| Create a team, public or private | members and admins; the creator is its only member; guests 403 |
| Join a public team, or leave any team | yourself (a guest joining a team they see: 403); a private team's last member can't leave or be removed (409 `Add someone else first`) |
| Add or remove team members | anyone in the team but guests, and admins (an admin joins a private team they aren't in, then adds others); only admins add a guest (403 `Only workspace admins can add a guest to a team`) |
| Make a team private or public | admins who see it; making one private needs a member (409 `Add a member first`) |
| Invite a guest | admins, naming at least one team (400 `Pick at least one team for a guest`) |

Team membership and privacy are managed from a browser session only (an API key gets 403), so agents never change them.

- A new workspace member joins every public team (people by invite, agents when added, the GitHub account when first connected) plus an invite's `teams`; a guest joins only their invite's teams.
- **Guests** see only their teams and do there what a member does with issues, docs, comments and projects, but set nothing up (403, after a 404 for what they don't see): no team settings, statuses, templates, workspace labels via `/api/labels` or by naming a new one on an issue (403 `Guests can't create workspace labels`; their teams' own labels they manage) or membership changes (they can leave). Views are empty (`GET /api/views` `[]`, a view 404, saving one 403), and the member list shows only people who share a team with them.
- **Views** whose filter names a team, project or parent issue you don't see are left out of `GET /api/views` and are 404.
- Relations to an issue you don't see are left out per viewer: `blockedBy`, `blocks`, `relatedTo`, `duplicates` and `children` drop it, `parent` and `duplicateOf` read null, `previousIdentifiers` and history drop what names teams you don't see, and doc refs (`Document.issues`, `Issue.docs`) drop it. Replacing a list (`blockedBy`, `relatedTo`, a project's `teams`) replaces only what you see. New relations to an issue you don't see are 404.
- An assignee or delegate must see the issue's team (400 `@x isn't in team BRD`, also on a move). An @mention of someone who doesn't see the team isn't recorded and notifies no one.
- The inbox: notifications go only to those who see the team; ones about something you no longer see are hidden (and not counted), and marking them by id is 404.
- A project is visible if any of its teams is; it shows only those teams, and its counts and progress count only what you see.
- Making a team private or public, joining, leaving, adding or removing someone, and a role change close the affected sockets (4401) so they reconnect with what they see now: everyone in the workspace for a visibility change, the person otherwise.
- Attachments uploaded in a team are that team's (see Attachments). Moving an issue or doc to another team moves the files its texts and comments link that were uploaded in its old team. Files with no team (uploaded before private teams, or in a project description) are the workspace's.
- **Known limits**: some answers reveal that something you don't see exists, because names are unique in the workspace: a team key a private team has (409 `Team key X is taken in this workspace`), a label or label group named like a private team's (409 `Label "x" already exists`, or 400 `… belongs to another team`), a doc or project slug (a derived one skips it: `plan-2`; a given one is 409), and a username filter naming a member you don't share a team with (it filters instead of 400 `Unknown`).

**Suspend** (`PATCH …/members/:username { suspended: true }`) ends access to that workspace at once (membership is checked on every request; their sockets close) and deletes their API keys and agent token there. If it was their last active membership, their sessions and unused sign-in links go too, so a reinstated person (`suspended: false`) signs in again with a link from the server's CLI; deleted keys never come back. Other workspaces are never touched. Suspending or demoting an admin also deletes the unused invites they made there. Suspended members stay listed, keeping their names in history. Removing an agent is suspending it; a new token reinstates it.

**Credentials.** Secrets are random and stored only as SHA-256 hashes, except those Docket signs or verifies with, kept in the clear: webhook and GitHub secrets (shown once, on create or rotate) and the VAPID private key.
- **Session**: the web UI's cookie `docket_session` (32 random bytes as hex; HttpOnly, SameSite=Lax, Secure over HTTPS, 30 days, re-sent while in use). Idle for 30 days (by `last_seen_at`, touched at most once a minute) and it's gone.
- **API key**: `Authorization: Bearer dk_<64 hex>`; it acts as its owner, in one workspace chosen when it's made (default: the request's), and sees nothing else (`/api/me`, `/api/workspaces`, lists, `/ws`): anything in another workspace is 404. People make their own (named, scope `read` or `write`) and revoke them. A read key gets 403 on anything but GET (REST) and on tools that change something (MCP). An agent's token is an API key it owns.
- **Managing access needs a browser session** (an API key gets 403): API keys, sessions, sign-in links, invites, creating a workspace, your profile and email, members, teams' membership and privacy, agents, webhooks, GitHub and push devices. A leaked key can't mint credentials that outlive it.
- **One-time codes**: 10 symbols of `A–Z 2–9` without `I O 0 1` (50 bits), shown as `XXXXX-XXXXX`, single-use, 15 minutes. A link is `<origin>/login#<code>`: the fragment never reaches the server, and the page removes it from the address bar.
  - **Invites** (a workspace, a role, optional teams) aren't tied to anyone: redeemed signed in, one adds you to the workspace (as your default profile, or the `name` and `username` you send); signed out, it creates an account and its membership (name, username, optional email).
  - **Sign-in links** open one person's account and may record a workspace: made by yourself (for another device; it records the workspace you're in), or on the server (`bun run sign-in-link <username> [workspace]`). The CLI finds the person holding that username (in that workspace, else in any; agents are refused); if several do, it exits 1 listing `<workspace key> · <name>` for each. Redeeming one while signed in as someone else deletes that session first.
- **Setup code**: while there are no users, the server prints one at startup (`DOCKET_SETUP_CODE` fixes it). `POST /api/setup` with it creates the first person, signed in, as admin of a new workspace. A wrong code is 403; once any user exists, 409.

**Rules for every request** (`auth.ts`):
- `/api/*` takes a session cookie or an API key, `/mcp` only an API key, `/ws` either. No or bad credentials: 401 (a stale cookie is also cleared). Not allowed (not an admin, read-only key, someone else's comment): 403. Outside your workspaces: 404.
- A cookie-authed WebSocket or non-GET request needs our own `Origin` (403 otherwise), since cookies ride along on same-site requests (a sibling subdomain, another localhost port); an invite joins the signed-in user only then.
- **Every data request acts in one workspace**: a key's own; else a session's `X-Docket-Workspace: <key>` (the web app sends the one its URL shows); else a session's only active workspace. Naming one you aren't an active member of, or a key naming another, is 404; a session in several that names none is 400 `Pick a workspace: send X-Docket-Workspace`. Team keys, identifiers and slugs resolve in it, and lists show only it. `/api/me`, sessions, sign-in links, `/api/workspaces…` and `/api/locate` need none; `POST /api/api-keys` needs one unless its body names `workspace`.
- A route that reads a body takes only `Content-Type: application/json` (the media type before any `;`, trimmed, case-insensitive, so `text/plain;charset=application/json` is refused), else 415; an upload takes only `application/octet-stream`. Neither is a CORS-simple type and Docket allows no CORS, so a cross-site page can't send one.
- Host check (DNS rebinding): `/api/*`, `/mcp` and `/ws` answer 403 unless the `Host` hostname (port ignored, case-insensitive) is `localhost`, `127.0.0.1`, `[::1]` or listed in `DOCKET_HOSTS`.
- Setup and code attempts: after 10 failures (401/403) from one client IP in a minute, 429 until the minute ends (behind a proxy, all clients share its IP).
- The app shell, manifest, service worker and icons are public; they hold no data.

**HTTP layer** (`http.ts`): every response carries `Content-Security-Policy` (everything `'self'`, plus Google Fonts' stylesheet and font hosts; `img-src 'self' data:`, so no remote image loads; `object-src`, `base-uri` and `frame-ancestors` `'none'`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and over HTTPS `Strict-Transport-Security`; API answers add `Cache-Control: no-store` (unless the handler set its own) and `Vary: X-Docket-Workspace`. In development, Bun's hot-reloading server serves the page itself. Request bodies over 1 MB answer 413 (uploads: over 10 MB); without a `Content-Length`, Bun cuts a body off at 11 MB. Texts are capped, else 400: titles 500 characters, names 200 (a member's or agent's: 60, on one line), descriptions and comments 100,000, doc content 500,000 (also after `edits`). Rate limit: a token bucket of 600 requests, refilling at 20 a second, per API key or session that signs in, never slowed by its IP's bucket; anything else (no credential, a wrong one however written, the public routes) per client IP (behind a proxy, all clients share its IP); across `/api`, `/mcp` and `/ws`; past it, 429 with `Retry-After`.

**Stale tabs**: tabs share one cookie, so the web app sends `X-Docket-User: <account id it shows>` (`Me.user.id`) with every request. If it's not the signed-in account (someone signed in as someone else in another tab), the request gets 401 `{ switched: true }` and the tab reloads as whoever is really signed in, instead of acting as them under the old name.

**Workspaces can't be deleted.**

**Authors** are never sent by clients: every write is attributed to the signed-in user or agent (Docket's own changes to @docket, on their behalf). Only a comment's author can edit or delete it (403 otherwise, with no admin override).

## Data

The schema lives in `schema.ts`, versioned by `PRAGMA user_version` (on a Durable Object, which refuses that pragma, a `docket_meta` row): a baseline at 29 (what migrations 1-29 left), then append-only migrations. A new database gets the baseline; one at 1-28 is refused at startup, to be upgraded through the release tagged `migrations-v29` first. Each migration is SQL or a function (for backfills and checks), run in its own transaction with foreign keys off; `PRAGMA foreign_key_check` must pass before it commits, else it rolls back and the server doesn't start. Foreign keys are on afterwards; WAL mode. A Durable Object can't turn foreign keys off, so there a migration defers them to its commit instead (a table rebuild there must not drop a table others reference: its ON DELETE actions would fire).

- **users**, **workspaces**, **workspace_members**, **sessions**, **api_keys**, **codes**: see Access.
- **teams**: id (internal; the API names teams by key), workspace, key (2–5 uppercase letters, unique within the workspace: `UNIQUE (workspace, key)`), name, description, next_number, default_status (where new issues start: a backlog or unstarted key; `defaultStatus` in the API), auto_close_parent and auto_close_children (0 or 1; `autoCloseParent`, `autoCloseChildren`: see Auto-close), auto_archive_days (`autoArchiveDays`: see Auto-archive), estimate_scale (`estimateScale`: see Estimates), cycle_weeks and upcoming_cycles (`cycleWeeks`, `upcomingCycles`: see Cycles), private (0 or 1; `private`: see Teams and guests), created_at, updated_at. `Team` also carries `member`: you're in it.
- **team_members** (see Teams and guests): team_id (cascades), user_id, created_at; primary key (team_id, user_id). A suspended member keeps their rows (reinstating brings the teams back) but counts nowhere while suspended.
- **workflow_statuses** (Linear's workflow: each team's own statuses): id, team_id, key, name, category, color, position; `UNIQUE (team_id, key)`, at most one triage status per team. Categories are fixed, in this order: `triage`, `backlog`, `unstarted`, `started`, `completed`, `canceled`; a team's statuses sort by category, then position (`Team.statuses`). The **key** (`a-z 0-9 _`, derived from the name: "In QA" → `in_qa`, a name with no Latin letters → `status_1`) is what issues, filters, history, notifications and webhooks hold, and never changes; the **name** (unique in the team, case-insensitively) and the color (`#rrggbb`, by default the category's: triage `#f76b15`, backlog `#a3a3a3`, unstarted `#8f8f8f`, started `#e8a800`, completed `#5e6ad2`, canceled `#b4b4b4`) can change, and a status moves within its category by position; its category never changes. A new team gets Backlog, Todo, In Progress, In Review, Done, Canceled and **Duplicate** (`duplicate`, canceled): a system status whose name, color and place are fixed and that can't be deleted. **Triage** is on while the team has a triage status (key `triage`, name "Triage" by default): nothing goes there on its own, only an explicit status (the Triage tab's New issue). **Deleting** a status is refused for Duplicate (400), the default status and the last non-Duplicate status of a category other than triage (409), and one that live or trashed issues are in unless `moveTo` names another status of the team (409 `3 issues are In QA: pass moveTo`); with it, those issues move in one transaction, each as its own status change would (history, `completed_at`, notifications, webhooks, change events). Deleting the triage status turns Triage off. Every change publishes `changed("team")`. Only people change a workflow (agents 403), in their workspace (another workspace's team is 404); agents read it from `list_teams`.
- **issues**: id, team_id, number (per-team sequence from `teams.next_number`; never reused after a delete), title, description, status (a key of its team's workflow), priority, labels (legacy JSON, unused: see issue_labels), assignee_id (a person), delegate_id (an agent), creator_id, parent_id, due_on, estimate, project_id and milestone_id (see Projects), cycle_id (see Cycles), created_at, updated_at, completed_at, archived_at (`archivedAt`: see Auto-archive), deleted_at (see Trash). Unique (team_id, number).
- **cycles** (see Cycles): id, team_id, number (1, 2, 3… per team; `UNIQUE (team_id, number)`), starts_at (00:00 UTC), ends_at (exclusive: the next cycle's starts_at, or when cycles were turned off), completed_at (when it ended and its unfinished issues rolled over).
- **Due date** (`due_on`, `dueOn` in the API; Linear's due date): a calendar date, `YYYY-MM-DD`, no time; null when there's none. It must be a real date (`2026-02-30`, `tomorrow`, `2026-9-1` are 400 `dueOn must be a date like 2026-09-30`); it sorts and compares as text. The due filters use the server's date, SQLite's `date('now')` (UTC; Docket has no per-person time zone): **overdue** is before today and not in a completed or canceled status, **soon** is today through 7 days ahead, **today**, **any** (has one), **none**. The web app colors dates against the browser's own date instead, so what someone sees matches their calendar; near midnight UTC the two can differ by a day.
- **Estimates** (Linear's, opt-in per team): a team's `estimate_scale` is null (off, the default) or one of four five-value scales (`ESTIMATE_VALUES` in types.ts): `exponential` 1, 2, 4, 8, 16; `fibonacci` 1, 2, 3, 5, 8; `linear` 1–5; `tshirt` XS, S, M, L, XL. An issue's `estimate` is a position 1–5 in its team's scale, not the value, so changing the scale changes how it shows, never what's stored; totals add the values, t-shirt sizes by position (XS 1 … XL 5). Setting `estimate` (null included) on a team with estimates off is 400 `Turn on estimates for this team first`; anything but an integer 1–5 or null is 400. Turning estimates off hides estimates without clearing them: the API answers `estimate: null` while the team's scale is null, and turning them back on (any scale) shows each issue's position again. A moved issue keeps its position, hidden or shown by its new team's setting; an `estimate` sent with a move is the new team's.
- **labels** (Linear's labels): id, workspace, team_id (null: a workspace label, usable on every team's issues; else that team's own, usable only on its issues), parent_id (its group), name, color (`#rrggbb`; new ones take the next of `LABEL_COLORS` by how many the workspace has), is_group, created_at. A **group** holds labels one level deep, is never applied itself, and its labels share its scope; an issue carries at most one label per group. A label's **path** is `Group/Name` in a group, else its name: what issues' `labels` hold, unique in the workspace case-insensitively (so a workspace label and a team label can't share one). New names can't contain `/` (names from before groups keep theirs). Labels outlive their issues: they're managed in settings, and trashed issues keep theirs.
- **issue_labels**: issue_id, label_id (both cascade). An issue's `labels` are its labels' paths, sorted case-insensitively. Writing `labels` (a whole-list replace, names or paths, case-insensitive) resolves each: a label's path; else a bare name of exactly one grouped label usable on the issue (`Bug` for `Type/Bug`; several are 400 `"High" is ambiguous: Effort/High or Impact/High`); else a new workspace label, or with `Group/Name` a new label in that group (the group found, or made as a workspace group). A group is 400 (`Type is a label group: pick one of its labels, e.g. Type/Bug`), another team's own label 400 (`Label "design" belongs to team WEB`), two labels of one group 400 (`Only one label per group: Type/Bug, Type/Feature`); a refused write creates nothing. Agents create labels this way too; only people manage them (Labels, under REST). Bulk `addLabels` with `Group/Name` swaps out the issue's label of that group; `removeLabels` takes a path or a grouped label's name.
- **issue_templates**: id, team_id, name, title, description, status (a status key, not a foreign key; null: the default at use time), priority (null: the default at use time), created_at, updated_at. **issue_template_labels**: template_id, label_id (both cascade). See Issue templates, under REST.
- **issue_aliases** (identifiers from before a move; see Moving an issue): team_id, number, issue_id (cascades on purge), created_at; primary key (team_id, number).
- **issue_blocks**: blocker_id, blocked_id. No cycles: setting `blockedBy` fails (400) if the issue itself or any issue it already blocks, directly or through a chain, is among the blockers.
- **issue_relations** (Linear's other two relations): from_id, to_id, kind (`related` or `duplicate`), created_at; primary key (from_id, to_id, kind). **Related** is two-way: one row per pair (lower id first), so `relatedTo` (a whole-list replace, like `blockedBy`) set on either issue shows on both; an issue can't be related to itself (400). **Duplicate** points one way: from_id duplicates to_id (the canonical issue), at most one per issue. Setting `duplicateOf` records it and sets the issue to its team's Duplicate status (`duplicate`, canceled category; the first canceled status if it had none), overriding a `status` sent with it; `null` clears it and leaves the status as it is. The issue itself, or one that already duplicates it directly or through a chain, is refused (400). The canonical issue lists its duplicates as `duplicates`.
- **issue_activity** (an issue's history, Linear's activity feed): id, issue_id (cascades on purge), actor_id, on_behalf_of_id (for changes Docket makes on its own, whose actor is @docket: whose change set them off; `onBehalfOf` in the API, else null), kind, from_value, to_value (JSON), created_at. One row per change, written as the last step of the change's own transaction, so a refused change (400, 409) writes none; the rows of one mutation share its actor and time. Kinds and values: `created` (creating also logs `assignee` and `delegate` when set), `team` the identifier before and after a move, `title` and `status` strings, `description` (no values: no diff), `priority` and `estimate` numbers (an estimate's position), `assignee` and `delegate` user ids (shown as `UserRef`s as they're known in the workspace now, so renames carry and suspended members keep their names), `labels` string arrays (paths as they were then: a label renamed or regrouped later still shows its old name there, and renaming logs nothing; deleting a label logs a `labels` change on each issue it came off, by whoever deleted it), `parent` and `duplicateOf` an identifier, `dueOn` a `YYYY-MM-DD` string, `blockedBy` and `relatedTo` identifier arrays, `claimed` the status before and after (keys), `project` a project's slug, `cycle` a cycle's number (a rollover's by @docket, from the ended cycle to the next; turning cycles off logs each issue leaving an upcoming one, by whoever did), `milestone` a milestone's name as it was then (like a label's path; deleting a milestone logs a `milestone` change on each issue it came off, by whoever deleted it), `trashed`, `restored`, `archived` and `unarchived` (no values). An update logs only fields that really changed (labels, blockers and related issues compare as sets); claiming your own started issue again logs nothing. Issues bumped by a relation change get no rows of their own.
- **comments** / **document_comments**: id, issue_id / document_id, author_id, body, created_at, edited_at, parent_id (a reply's thread root, in the same table and on the same issue or doc; null for a root), resolved_at and resolved_by_id (roots only). **Threads** (Linear's replies, one level): a reply to a reply joins its root's thread; a parent that isn't a comment on the same issue or doc is 404 `Comment N not found`. Anyone who can comment resolves or reopens a thread, from its root only (a reply is 400 `Resolve a thread from its first comment`); resolving twice changes nothing. A new reply reopens a resolved thread. A root with replies can't be deleted (409 `This comment has replies; edit it instead`). Replies notify like any comment (`commented`, or `mentioned`).
- **reactions** (Linear's emoji reactions, on the issue description, a comment or a document comment; not on document bodies): target (`issue:<id>`, `comment:<id>` or `document_comment:<id>`, the same convention as `mentions.source`), user_id, emoji, issue_id / document_id (whichever the target is on; cascades on purge), created_at; primary key (target, user_id, emoji). `PUT`/`DELETE …/reactions/:emoji` (issue description, issue comment, document comment) add or remove your own; idempotent both ways, and at most 20 distinct emoji per target (409 beyond, only when adding a new one). An emoji is validated as a single grapheme with a pictographic or regional-indicator code point (or a keycap), at most 32 UTF-16 units, stored trimmed and NFC-normalized; anything else is 400 `emoji must be a single emoji, e.g. 👍`. Reactions never bump `updated_at`, log activity, notify anyone or send a webhook event, only `changed("issue" | "document", …)`; deleting a comment deletes its reactions.
- **subscriptions** (who follows an issue or doc, Linear's subscribers): user_id, issue_id or document_id (exactly one; cascades on purge), created_at; unique per user and issue or doc. You're subscribed when you create an issue or doc, claim an issue, are assigned it, have it delegated to you, are @mentioned in its description, content or a comment, or comment on it; unsubscribing sticks until one of those happens again. `PUT`/`DELETE …/subscription` (and MCP `subscribe`) follow or unfollow by hand.
- **notifications** (the inbox): id, user_id (the recipient), workspace, kind, actor_id, issue_id or document_id (cascade on purge), comment_id (in `comments` or `document_comments`; no FK), status, created_at, read_at. Written in the mutation's own transaction, only for active members of the workspace who see the team, never for the actor. Kinds: `assigned` (you became the assignee), `delegated` (an issue was delegated to you, an agent), `mentioned` (a new @mention of you in a description, doc content or comment, with the comment if it's in one; editing a text notifies only mentions it didn't have), `commented` (a new comment on something you follow; not to those it mentions, who get `mentioned`), `status` (an issue you follow moved into a completed or canceled status, or into `in_review` where the team has it; marking it a duplicate included; other changes, claims and relations included, notify nobody). Deleting a comment deletes its notifications. Each person keeps their newest 2,000 per workspace; older ones go as new ones arrive.
- **push_subscriptions** (a device's Web Push subscription): id, user_id, session_id (cascades: signing out, revoking the session or its idling out drops it; an idle session is deleted before any push to its user), endpoint (unique), p256dh, auth, created_at. **vapid_keys**: Docket's one VAPID key pair (base64url), made on first use.
- **documents**, **document_versions**, **document_refs**: see Documents.
- **projects**, **project_teams**, **milestones**: see Projects.
- **custom_views**, **view_favorites**: see Views.
- **attachments**: see Attachments.
- **github_integrations**, **issue_links**: see GitHub.
- **webhooks**: id, workspace (cascades), url, label, resource_types (JSON array), secret (in the clear: it signs), enabled, failures (deliveries in a row that failed for good), created_by, created_at, updated_at. See Webhooks.
- **webhook_deliveries** (the outbox and its log): id, webhook_id (cascades), uuid (`Docket-Delivery`), type, action, entity (identifier, slug, comment id or notification id), payload (JSON without `webhookTimestamp`), status (`pending`, `delivered`, `failed`), attempts, next_attempt_at, response_status, error, created_at, last_attempt_at. Kept 7 days.
- **mentions** (who is @mentioned where; the inbox and webhooks act on them): source (`issue:<id>` for a description, `comment:<id>`, `document:<id>` for content, `document_comment:<id>`), user_id, issue_id / document_id (the issue or doc it's in or on; cascades on purge), author_id, created_at; primary key (source, user_id). Recomputed in the same transaction as every save of the text, like doc refs: mentions the text still has stay as they were (same author and time), new ones get the saver and the save's time, dropped ones go; deleting a comment deletes its rows. Not in the API. **Syntax** (`MENTION_PATTERN` in types.ts, shared with the renderer): `@username` (`[a-z0-9][a-z0-9._-]{1,31}`, case-insensitive, not followed by another username character), not preceded by a letter, digit, `_ . @ / + -` (so `bob@example.com` and `https://x.com/@ana` aren't mentions), in prose: never in code (fenced, indented or inline) or link text. If no one holds the whole match, trailing `. _ -` drop one at a time (`Thanks @ana.` mentions ana). It counts only for an active member of the text's own workspace, people and agents; no one mentions themselves (one someone else made stays when they edit the text). In doc content only, a match that ends exactly at the end of the content doesn't count yet (the editor autosaves mid-word: `@al` on its way to `@alice`); `@al ` or more text after it does.

Identifier = `${team key}-${number}`, parsed case-insensitively, resolved in the request's workspace (`BRD-1` can exist in several); an identifier an issue had before it moved team resolves to it too (everywhere one is read: routes, MCP, relation fields, filters, doc refs, `/api/locate`). Parents, blockers, related and duplicate issues and doc refs never cross workspaces (an identifier from another workspace is 404). Any change to an issue or its comments bumps `updated_at`, strictly forward (at least 1 ms past its previous value, even within one millisecond), since it doubles as the version token for `baseUpdatedAt`; Creating an issue with a parent, blockers, related issues or a canonical issue bumps and publishes them. Moving an issue to or from the trash also bumps and publishes its sub-issues, its parent, the issues it blocked or was blocked by, its related issues, its duplicates and the issue it duplicates; docs that mentioned it get a `document` event. Changing an issue's parent, blockers, related issues or `duplicateOf` likewise bumps and publishes the old and new parent, each blocker or related issue added or removed, and the old and new canonical issue. `completed_at` is set when the status enters the completed or canceled category, cleared when it leaves (a move within them keeps it). New issues start in the team's default status (backlog unless changed). A status is given by key or, failing that, name, case-insensitively, from the issue's own team only (else 400 `Invalid status "x" for BRD. Use one of: …`). List order: status category, then the team's order, then priority (1→4, then 0 last), then `updated_at` desc; a bad or outdated cursor is 400 `Invalid cursor: pass an endCursor from a previous page`. `sort=due` instead puts the earliest due date first and issues without one last, then that same order; page cursors carry both orders' keys.

**Moving an issue** (Linear's, within its workspace): `PATCH { team }` (or MCP `update_issue`) moves it to another team of its workspace. It takes that team's next number (`WEB-5`), and its old identifier goes to `issue_aliases`, so old links, bookmarks and mentions keep resolving to it; `previousIdentifiers` (on `IssueSummary`, oldest first) lists them. A team key resolves only in the request's workspace, so another workspace's team, like an unknown one, is 400 `Unknown team "X": an issue moves only to a team of its workspace`; moving to its own team changes nothing. Its **status** carries over by key if the new team has it, else becomes that team's first status of the same category (not Duplicate), else the team's default (Triage into a team without it); a `status` sent with the move is the new team's (400 otherwise, and nothing moves), and `completed_at` follows categories as usual. Its old team's own **labels** come off (workspace labels stay), unless `labels` is sent with the move, resolved in the new team. It keeps everything else: parent, sub-issues, blockers, related and duplicate issues, comments, reactions, subscribers, mentions, attachments, due date and doc refs all point to its row; it keeps its project and milestone, and its new team joins the project (`project_teams`). One mutation, one history line: `team` (old and new identifier), plus `status`, `labels` and `cycle` if they changed; one webhook `update` whose `updatedFrom` has the old `id`, `team` and `number`; no notification of its own (a status change it causes notifies as usual); `changed("issue")` for both the old and the new identifier. Bulk edits don't move issues.

**Auto-close** (Linear's per-team settings, both off by default; people switch them in team settings, `PATCH /api/teams/:key`, or MCP `update_team`). Only an issue's own status change sets it off (a PATCH, bulk edit or MCP `update_issue` that moves it into the completed or canceled category from outside them), never creating, claiming, trashing, deleting a status, or reopening: closing cascades, reopening doesn't. **Sub-issues** (`autoCloseChildren`, the closed issue's team): its live, unarchived sub-issues not yet completed or canceled move to the same status: the same key in their own team, else that team's first status of the same category that isn't Duplicate (a parent marked Duplicate gives Canceled); ones already closed are left alone. **Parent** (`autoCloseParent`, the parent's team): when every live, unarchived sub-issue of a live, unarchived, open parent is completed or canceled, the parent moves to its team's first completed status (never canceled, even if every sub-issue was). Each issue closed this way sets off the same rules in turn, so it cascades down the tree and up the chain of parents. It all happens in the triggering change's transaction; each closed issue gets `completed_at`, a bump, a `changed` event, its own `status` history row by **@docket** with `on_behalf_of_id` the person or agent who made the change, and the usual status notification and webhook `update` with @docket as actor.

**Trash** (Linear's delete): deleting an issue or doc sets `deleted_at` (`deletedAt` in the API). It leaves lists, search, labels' open counts (its labels stay on it and in the label list), team counts, relations (`blockedBy`, `blocks`, `relatedTo`, `duplicateOf`, `duplicates`, sub-issues) and doc refs, but keeps its links, so restoring (`POST …/restore`) puts everything back. Sub-issues of a trashed issue stay, still pointing at it. A trashed item can be read (with `deletedAt`) and restored, nothing else: edits, comments, claims and new relations to it answer 409 or 400. After 30 days in the trash it's deleted for good (with its comments, versions and refs), at startup and whenever something is trashed, restored or the trash is listed. Deleting or restoring twice is 409.

**Auto-archive** (Linear's, opt-in per team): `autoArchiveDays` (null by default: never), set in team settings or `PATCH /api/teams/:key`. In a team with it set, an issue completed or canceled for that many days is archived (`archived_at`, `archivedAt` in the API) by **@docket**, with no `onBehalfOf`; the sweep covers every team and runs at startup, hourly, and after an issue update that closes an issue. An archived issue is left out of issue lists unless `archived=true` or `q` is given, still opens by id or identifier, and can still be linked to (parent, blocker, related, duplicate); edits, comments and claims are 409 until it's unarchived. `POST …/archive` and `…/unarchive` work on a live (non-trashed) issue, logged as `archived`/`unarchived` by whoever did it; twice is 409.

**Cycles** (Linear's, opt-in per team): repeating planning periods, numbered per team ("Cycle 12", no names), 1–8 weeks long, on UTC dates (00:00 UTC; teams have no timezone). People turn them on in team settings or `PATCH /api/teams/:key { cycleWeeks, cycleStartsOn?, upcomingCycles? }` (agents 403, another workspace's team 404): the next number (1 for a new team, else one past the last, so turning them on again continues the numbering) starts on `cycleStartsOn` (today by default; before today is 400), and `upcomingCycles` (1–15, default 2) upcoming cycles are kept ready after it. A cycle is **completed** once it ended, **current** while it runs, **upcoming** before it starts. **Rollover**: when a cycle ends, it's completed and its unfinished issues (every live one not in the completed or canceled categories, triage and backlog included; not trashed or archived ones) move to the next cycle, bumped, as @docket's `cycle` change with no `onBehalfOf` (history, webhooks, change events); finished ones stay. `syncCycles` does this idempotently, one transaction per team: at startup, every minute before a team's cycles are listed or one is assigned, and after its cycle settings change; it also tops up the upcoming cycles, after the last. A new `cycleWeeks` re-dates only cycles that haven't started, back to back from the current one's end (the current one keeps its dates, past ones never change); a lower `upcomingCycles` deletes none. `cycleWeeks: null` turns them off: the current cycle ends now (`endsAt` = then) keeping its issues, the upcoming ones are deleted and their issues leave them (bumped, logged by whoever turned them off), and completed ones stay. `cycleStartsOn` otherwise is 400 `cycleStartsOn only applies when turning cycles on`. An issue's `cycle` is a number of its team's, `"current"`, `"next"` (the first upcoming) or null; 400 for a team without cycles (`WEB doesn't use cycles`), an unknown number (`Unknown cycle 99 in WEB`), a completed one (`Cycle 3 is over`) and `"current"` before the first starts (`WEB has no current cycle`). A new sub-issue in its parent's team, created in an unstarted or started status with no `cycle`, joins its parent's cycle unless that one's over. Cycles are per team, so a moved issue leaves its cycle unless the move names one of its new team's. Projects and cycles are independent: an issue can be in both. Cycle progress counts issues like a project's (estimates don't weigh in).

**Assignee and delegate** (Linear's model): the assignee is a person who owns the issue; the delegate is an agent working on it for them. Each must be an active member of the issue's workspace of the right kind (400 otherwise, e.g. `assignee: claude-a is an agent; set it as the delegate`). `me` means the caller, in values and filters.

**Claim** (`POST /api/issues/:id/claim`, MCP `claim_issue`): a person takes the assignee slot, an agent the delegate slot; an issue not started yet (triage, backlog or unstarted category) moves to the team's first started status (`in_progress` by default), one already started keeps its status. One IMMEDIATE transaction reads and writes, so of two claims racing for a free issue exactly one wins. A completed or canceled one is 409 `"<ID> is <status key>"` (`BRD-2 is done`); one whose slot another active member holds is 409 `"<ID> is claimed by <username>"` (a suspended holder doesn't count). Claiming your own started issue again changes nothing. To hand it back, clear the slot and set status todo.

**Issue versions**: `IssuePatch.baseUpdatedAt`: if present and different from the current `updatedAt`, the PATCH (or `update_issue`) answers 409 `{ "error": "Issue changed since you read it" }` and changes nothing; the check and the write share one IMMEDIATE transaction. Comments bump `updatedAt` too, so send it where lost updates happen (description, and the whole-list `labels`, `blockedBy` and `relatedTo`), not for single-field changes like status or priority.

A name is required (200 characters) and can't contain `/` (400 `Use a group for Group/Label…`); a taken path is 409 `Label "Type/Bug" already exists`; a color must be `#rrggbb`. `isGroup` only on create; a group can't be in a group (400), and a label in a group has its group's scope (400 otherwise). Rescoping (`team`: a key of the workspace, or null) is 409 `Used on 3 issues outside WEB` if an issue (trashed too) of another team carries it; a group takes its labels along. Moving a label into a group is 409 if an issue would then carry two of it. Renaming or regrouping changes the path on every issue carrying it (a group's: its labels'): they're bumped and published, so a stale whole-list write gets `baseUpdatedAt`'s 409, with no history row or webhook event. Deleting is for good: it comes off every issue (trashed too), each logging a `labels` change (history, webhooks); a group with labels is 409 `Move or delete its labels first`. Every change publishes `changed("label")`.

**Issue templates** (per team) are managed by people only (agents 403); another workspace's or team's template is 404. `name` is required; `title` and `description` default to `""`, `status` and `priority` to null (the defaults at use time). `status` is checked against the team's workflow when set (400 `Invalid status "x" for BRD…`); if that status is deleted later, the template falls back to the team's default. `labels` resolve and write as an issue's do (Data). `POST /api/issues` and MCP `create_issue` take `template` (a template id of the issue's team, else 404): its fields apply first, then the body's own, then the usual defaults. Deleting a template is for good and leaves issues made from it alone. Changes publish `changed("team")`.

`Issue` and `Document` carry `subscribed` (you, the caller). A `Notification` is `{ id, kind, workspace, actor, issue: { id, title, status } | null, document: { slug, title } | null, comment: { id, excerpt } | null, status, createdAt, readAt }`: the excerpt is the comment's first 200 characters as plain text (its markdown's text: link text without its URL, code without backticks, an image's alt text, no HTML tags), with runs of whitespace as one space, read when listed (an edit shows). Only the recipient ever sees, marks or deletes a notification: an id that isn't yours in the request's workspace is 404, and nothing changes.

A `Comment` is `{ id, author, body, createdAt, editedAt, parent, resolvedAt, resolvedBy, reactions }`: `parent` is its thread's root id (null for a root), `resolvedAt`/`resolvedBy` are set on a resolved root. `Issue.comments` and `Document.comments` stay one flat list by id; clients group by `parent`. Editing a comment sets `editedAt`; deleting is permanent. Adding, editing, deleting, replying and resolving bump the issue; doc comments never bump the doc; reactions bump neither. A `Reaction` is `{ emoji, users }`, `users` (`UserRef[]`) in the order they reacted; `reactions` is ordered by first reaction. `Issue.reactions` are the description's.

## Realtime

`GET /ws` upgrades to a WebSocket that subscribes to the caller's workspaces (a key's: only its own). After every mutation (REST or MCP) the server publishes a `ServerEvent` `{ type: "changed", entity, workspace, id }` (`entity`: `workspace`, `member`, `team`, `issue`, `document`, `label` (`id`: its id), `project` (`id`: its slug), `view` (`id`: its id) or `inbox`) to that workspace's sockets only, and a team's only to sockets that see the team (`eventTeams` in tracker.ts, topics in app.ts): an issue's (by its identifier's key), a doc's, a team, a team's own label (a deleted one's too: its row is gone, so the delete names the team) or a project's (its teams) go to `public:<ws>` for a public team, heard by everyone in the workspace but guests, and to `team:<id>`, heard by a private team's members and a public team's guests; a member's goes to `public:<ws>` and their teams' `team:<id>`, so a guest hears only of members who share a team with them (a guest in no team: of themselves, on their own sockets), and a view's to `public:<ws>` alone, since guests can't use views; anything else goes to `workspace:<ws>`, heard by everyone there. A socket's topics are fixed when it opens; any change to what its user sees closes it (see Teams and guests). Three go to one person alone, on their sockets in that workspace (a key's socket: only its own): `inbox` (`id`: their username) whenever their notifications change, `issue`/`document` when they follow or unfollow it, and `view` when they star or unstar it. The UI refetches what it's showing (the inbox and its sidebar count only on `inbox` events). Signing out, revoking a session or key, suspension and agent token changes close the affected sockets (code 4401); clients reconnect with what's current.

## Push notifications

Linear's mobile notifications, through Web Push (`push.ts`): every notification a **person** gets (Data, above) also goes to each device they turned push on for, in any workspace, as `{ title, body, url }`: the issue's identifier and title (a doc's title), what happened as the inbox says it ("Ana commented: …", "Ana moved to Done"), and `/<workspace>/issue/<id>` or `/<workspace>/doc/<slug>`, which tapping it opens (`sw.js`, in a Docket window already open if there is one). Agents' notifications never push (they have webhooks). A push leaves after the notification's transaction commits and reads it then, so a rolled-back or already deleted one never goes; it's encrypted to the device (`aes128gcm`), VAPID-signed, with a one-day TTL, and a subscription its push service calls gone (404, 410) is deleted.

**Devices**: Account settings, Notifications, turns push on for this device (the browser asks for permission; on iPhone and iPad, only for Docket added to the Home Screen, iOS 16.4 or later) and off, and sends a test. Only a signed-in browser session manages them (an API key gets 403). A subscription belongs to the session that sent it and goes when that session is signed out or revoked; the app sends it again on every start while the browser still has it and permission, so signing in again brings it back without asking, and a device another account signs in on moves to them. **Endpoints** must be `https:` on a browser push service's host, with no port or credentials: `web.push.apple.com`, `fcm.googleapis.com`, `android.googleapis.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com` (400 otherwise), so Docket never posts anywhere else; redirects aren't followed. The VAPID subject is Docket's public URL (`DOCKET_URL`, else the server's) when it's https, else `https://github.com/youssefaltai/docket`.

## Webhooks

Linear's webhooks (`webhooks.ts`): a workspace's changes are POSTed to an HTTP endpoint as they happen. Each webhook belongs to one workspace and hears only it; payloads use that workspace's usernames and `/<ws>/…` URLs.

**Who**: workspace admins, in a browser session (`requireAdminSession`): an API key or a member gets 403, anyone outside the workspace 404 (a webhook id of another workspace too). No MCP tools. Every write publishes `changed("workspace")`. A webhook hears the whole workspace, private teams included (a `Notification` event only ever goes to an agent that sees the team).

| Method | Path | Body | Returns |
|---|---|---|---|
| GET / POST | /api/workspaces/:key/webhooks | `WebhookInput` `{ url, label?, resourceTypes? }` (default: all four) | `Webhook[]` (never the secret); 201 `{ webhook, secret }` |
| PATCH / DELETE | /api/workspaces/:key/webhooks/:id | `WebhookPatch` `{ url?, label?, resourceTypes?, enabled? }` (other fields: 400) | `Webhook`; `{ ok: true }` (its log goes too) |
| POST | /api/workspaces/:key/webhooks/:id/secret | | `{ secret }`: the old one stops at once |
| GET | /api/workspaces/:key/webhooks/:id/deliveries | | `WebhookDelivery[]`, newest 50 |

`resourceTypes` is a non-empty subset of `Issue`, `Comment`, `Document`, `Notification`. Enabling resets `failures`; disabling fails its queued deliveries ("webhook disabled"). The secret is `dkwh_` + 32 random bytes as hex, returned only by create and rotate.

**Events** (`WebhookPayload`): `{ action, type, workspace, actor, createdAt, data, updatedFrom?, url, webhookId, webhookTimestamp }`. `action` is `create`, `update` or `remove`; `createdAt` when the change happened; `url` the entity in the web app (`DOCKET_URL` or the server's address, plus `/<ws>/issue/KEY-1` or `/<ws>/doc/slug`); `webhookTimestamp` the attempt's time in ms. An update carries `updatedFrom`: the previous values of the fields that changed. One mutation (REST or MCP) sends at most one event per entity; a change that changes nothing sends nothing. `data` by type:
- **Issue**: `IssueSummary & { description, creator }`. Create; update (`updatedFrom` by field: `title`, `description`, `status`, `priority`, `estimate`, `labels`, `assignee`/`delegate` as `UserRef` or null, `parent`, `blockedBy`, `relatedTo`, `duplicateOf`, `dueOn`, `project`, `milestone`, `cycle`; a move gives the old `id`, `team` and `number`; a claim gives the status and the slot it took; archiving and unarchiving give `archivedAt`); `remove` = moved to the trash; restoring is an `update` with `updatedFrom: { deletedAt }`. Issues bumped only by a relation change send nothing.
- **Comment**: `Comment & { issue: identifier | null, document: slug | null }` (a reply carries its `parent`); update carries `updatedFrom: { body, editedAt }` (only when the body changed), or `updatedFrom: { resolvedAt }` when its thread is resolved or reopened (a reply that reopens one sends the root's update first); remove carries the comment as it was.
- **Document**: `DocumentSummary`, never the content (fetch it). Update's `updatedFrom` always has `updatedAt`, plus `title`, `team`, `position`, `project`, `updatedBy` when they changed; a content change shows as `updatedAt` alone. Updates wait 10 s: saves within that window (autosave) merge into the one queued, unattempted delivery for that doc (newest `data` and actor, oldest `updatedFrom`). Any other event of that doc (trash, restore) sends a held update at once, first. Restore is an update with `updatedFrom: { deletedAt }`, sent at once.
- **Notification**: `Notification & { user }`, `action: "create"`, only for notifications whose recipient is an **agent** (people's are never sent). This is the agent trigger: `data.kind` `delegated` (an issue was delegated to it), `mentioned` (with `data.comment` when in a comment), `commented`, `status`.

Within one mutation, the entity's own event is queued before the notifications it causes (an issue's `create` before its `delegated`).

**Delivery**: an outbox. Each event is written as one `pending` delivery per enabled webhook of the workspace that takes its type, in the mutation's own transaction (a refused change sends nothing). A background loop (`startWebhooks`, from `index.ts`) sends what's due, oldest first, up to 4 at a time and one at a time per webhook, so a webhook's deliveries arrive in order; a write schedules a pass right after it commits, a retry at its time, and a 1 s interval catches anything left (after a restart). Each attempt re-checks the target, then `POST`s with a 5 s timeout, never following redirects, headers `Content-Type: application/json`, `User-Agent: Docket-Webhook`, `Docket-Delivery: <uuid>` (the same on every attempt), `Docket-Event: <type>`, `Docket-Timestamp: <ms>`, `Docket-Signature: <hex HMAC-SHA256 of the raw body with the secret>`. **Verify**: compute the HMAC over the raw body bytes and compare in constant time; reject a `webhookTimestamp` more than a minute off (replays). Any 2xx is delivered and resets the webhook's `failures`. Anything else (another status, a redirect, a timeout, a network error, a blocked target) retries after 1 minute, 1 hour and 6 hours; after the 4th attempt the delivery is `failed` and `failures` += 1; at 10 failures in a row the webhook is disabled (`enabled: false`; the UI says "Disabled after 10 failed deliveries") and its queued deliveries fail. Only the status code and a short error are kept (`HTTP 500`, `timeout after 5 s`, `network error: ConnectionRefused`, `blocked: 10.0.0.5 is private`), never response bodies. Deliveries older than 7 days are deleted at startup and hourly.

**Targets** (`checkTarget`), checked on create and update (400 `Webhook URL refused: <why>`) and before every attempt: `https:` only; no user or password in the URL; the host must resolve (`dns.promises.lookup`, all addresses) and **every** address must be public: not IPv4 0/8, 10/8, 100.64/10, 127/8, 169.254/16 (cloud metadata), 172.16/12, 192.0.0/24, 192.168/16, 198.18/15, 224/4, 240/4, nor IPv6 `::/96` (`::`, `::1`, IPv4-compatible), fc00::/7, fe80::/10, ff00::/8; IPv4-mapped (`::ffff:0:0/96`) and NAT64 (`64:ff9b::/96`) addresses are checked as the IPv4 inside. Numeric host forms (`127.1`, `0x7f000001`, `2130706433`) are normalized by the URL parser first. `DOCKET_WEBHOOK_ALLOW_PRIVATE=true` lifts the address rule and allows `http:` too, for agents on the same host or tailnet; set it only when every admin may reach the server's network. Known limit: DNS can answer differently between the check and the connect (rebinding); redirects are never followed, so a public endpoint can't bounce a delivery inward.

## GitHub

Linear's GitHub integration, the core of it, with no GitHub App and no dependency (`github.ts`): each workspace can receive GitHub's webhook, which links pull requests and commits to issues by identifier and moves them along. Docket never calls GitHub, so there are no linkback comments and nothing beyond what the payload says. Deliberate differences from Linear: the automation and the branch format are fixed, not settings.

**Connecting** (workspace admins, in a browser session, like webhooks: an API key or a member gets 403, anyone outside the workspace 404; no MCP tools). Each write publishes `changed("member")` for the account.

| Method | Path | Returns |
|---|---|---|
| GET | /api/workspaces/:key/github | `GitHubConnection` `{ connected, url, account }`: `url` is the payload URL (the request's origin + `/api/github/<workspace>`), `account` GitHub's account (null before the first connect); never the secret |
| POST | /api/workspaces/:key/github | 201 `{ url, secret }`: connects (making the account, or reinstating it), or issues a new secret, which replaces the old one at once. The secret (`dkgh_` + 32 random bytes as hex) is shown only here |
| DELETE | /api/workspaces/:key/github | disconnects (409 if it isn't connected): the secret is cleared, so every delivery is refused, and the account is suspended (history keeps "GitHub") |

**The account**: connecting makes an agent account in the workspace, "GitHub", username `github` (else `github-2`, `github-3`… if that's taken there), with no key. Every change the integration makes is an ordinary `updateIssue` by it, so history ("GitHub moved from In Progress to In Review"), notifications, webhooks, realtime and auto-close (by @docket on @github's behalf) work as for anyone's. See Accounts for what it can't be.

**The webhook**: `POST /api/github/:workspace`, public (outside `guard`). In order: a declared `Content-Length` over 1 MB (413) and the rate limit (429); the Host check (403, as for `/api/*`); `Content-Type: application/json`, else 415 `Set Content type to application/json in GitHub's webhook settings`; the body read, over 1 MB 413; then `X-Hub-Signature-256` must be `sha256=` + the hex HMAC-SHA256 of the exact body bytes with the workspace's secret, compared in constant time. An unknown workspace, one not connected, and a missing or wrong signature all answer the same 401 `Invalid signature` (an unknown workspace is checked against a random secret, so it takes as long). Only then is the body parsed (400 if it isn't JSON). The rate limit is the usual token bucket, per client IP (the route takes no credential, so made-up headers can't mint buckets). GitHub signs no timestamp, so a captured delivery could be replayed; replays are harmless (links are upserts, and the automation only moves issues forward, once per new closing link or change of its state; a `merged` link stays merged and never moves an issue again, so a replay can't re-close through it). `X-GitHub-Event`:
- `ping`: 200 `{ ok: true }`.
- `pull_request` with action `opened`, `reopened`, `edited`, `ready_for_review`, `converted_to_draft`, `closed` or `synchronize` (others: 200 `{ ignored: "pull_request labeled" }`): links the PR (its `html_url`, title, number and state: `merged` if merged, else `closed`, else `draft` or `open`) to every issue it refers to.
- `push`: each commit (at most 100) whose message has a magic-word statement links as a `commit` (its `url`, the message's first line as title). Pushed to `refs/heads/<repository.default_branch>`, closing commits move their issues to done (below), once: the link's state becomes `merged`, so a replayed push moves nothing (commits merged before this rule have no state, so one redelivery of their push can close a reopened issue once more).
- Anything else: 200 `{ ignored: "<event>" }`. Handled events answer 200 `{ linked: ["DKT-12"], moved: { "DKT-12": "in_review" } }`, so GitHub's delivery log explains itself.

**Linking rules**: an identifier (`KEY-12`, case-insensitive, at most 50 per PR or commit) links only a live issue of the connected workspace: one it had before a move resolves too, while unknown ones, another workspace's, trashed and archived issues are ignored (not in `linked`). **Closing** references: an identifier in the branch name (`(^|[/_-])KEY-12(?=$|[/_-])`, case-insensitive: `ana/dkt-12-fix-login`), a bare uppercase one in the PR title (`DKT-12: fix`; lowercase `utf-8` isn't one), and any after a closing word in the title or body. **Contributing** references: after a contributing word in the title or body; a contributing reference wins over a closing one. A statement is the word, an optional `:`, then identifiers separated by `,`, `&` or `and` (`Fixes DKT-1, DKT-2 and DKT-3`); a bare identifier in a body or commit message doesn't link. Closing words: close(s/d), closing, fix(es/ed/ing), resolve(s/d), resolving, complete(s/d), completing, implement(s/ed/ing). Contributing words: ref, refs, references, part of, related to, contributes to, towards, updates. PR titles and URLs are GitHub's: stored as plain text, the title on one line (runs of whitespace as one space, at most 500 characters); a PR or commit whose URL isn't http(s) is ignored.

**issue_links**: issue_id (cascades), url, kind (`pull_request` or `commit`), title, number (PRs), state (PRs: `draft`, `open`, `merged`, `closed`; commits: `merged` once pushed to the default branch, else null), closes (1 closing, 0 contributing), created_at, updated_at; primary key (issue_id, url). A new or changed link bumps the issue and publishes `changed("issue")` (no history row). `Issue.links` (`IssueLink[]`: PRs, then commits, oldest first). **github_integrations**: workspace (primary key, cascades), user_id (the account), secret (in the clear; NULL: disconnected), created_by, created_at.

**Automation** (fixed, closing links only, by status category, as the account; when the link is new or its state or closing changed, so a push to an open PR or a retitle never moves an issue someone moved back by hand; a `merged` link stays merged and never moves an issue again): a **draft** PR moves a triage, backlog or unstarted issue to its team's first started status; an **open** (opened, reopened, ready) PR moves it, or a started one, to `in_review` where the team has that status; a **merge** moves anything not completed or canceled to the team's first completed status, unless another closing PR linked to the issue is still open or a draft. A closing commit on the default branch closes like a merge (same guard). Closed unmerged: the state only. Completed and canceled issues never move.

**Branch names**: `Issue.branchName` is for the caller: `<username>/<key>-<number>[-<slug>]`, lowercase: `ana/dkt-12-fix-login`. The slug is the title's (as for doc slugs), cut at a dash to at most 40 characters, and left out when nothing Latin is left (an Arabic title: `ana/dkt-12`). The username is made ref-safe: runs of `.` become one, and a trailing `.` or `.lock` gets a `-` for its dot (`a..b.lock` → `a.b-lock`).

## MCP

Streamable HTTP at `/mcp`, stateless (a new server and transport per request, JSON responses). Server name `docket-<workspace>`, title `Docket · <Workspace name>`, `websiteUrl` the public origin (`DOCKET_URL`, else the request's). Tool descriptions must explain the conventions (workspace → team → issue/doc, statuses, priority numbers, identifiers, assignee vs delegate) so an agent can use them without reading docs. ### Keyboard

`⌘K`/`Ctrl+K` opens the command menu (see UI) from anywhere, even while typing in a field, except inside the rich editor (which keeps `⌘/Ctrl-K` for links) or while a popover or modal is open. `Esc` closes it; `Tab` closes it without refocusing; `↓`/`↑` (or `Ctrl-N`/`Ctrl-P`) move the active row; `Enter` runs it.

The keys and what they do are `SHORTCUT_GROUPS` in `src/web/shortcuts.tsx`, which is also the `?` help. What that list doesn't say:

- Page shortcuts never fire while typing in a field, in a popover, or during IME composition. The exception is `⌘⇧.` / `Ctrl+Shift+.` (copy the issue's branch name), which works while typing too and matches `e.code === "Period"`.
- `J`/`K`/`↓`/`↑` move focus over issue, triage, cycle, docs and project lists and boards, the inbox, My Issues and views. `U` and `Alt-U` match by key position, so Option-U works on a Mac.
- A `G` chord arms a 900ms window for its second key; an unbound second key, or none within the window, doesn't navigate. The second key is consumed either way, so it never also triggers a page shortcut (`G` then `P` doesn't open the priority picker).
- `S`, `P`, `A`, `D`, `L`, `I` and `⌘/Ctrl-⌫` act on the focused row or the issue page (`D` and `L` on the issue page only); the delete comes with Undo. With a selection (where Multi-select under UI works), `S`/`P`/`A`/`D`/`L` open that picker in the bulk bar for every selected issue, and `⌘/Ctrl-⌫` trashes them all after one confirm; `I` always claims the focused row.
- `Esc` clears the issue selection if any, else closes the mobile nav if open, else leaves an issue, doc or project page for the last list of its kind, else blurs (on a doc page, first it leaves editing, the version preview, then history). In a popover picker it closes and refocuses the trigger; `Tab` closes without refocusing. Pickers include the property pickers, filters, the bulk bar, the workspace switcher and the account menu.

Elsewhere: `Enter` saves an inline title (issue/doc) by blurring; `⌘/Ctrl-Enter` saves or sends (description, comments, modals); `Esc` reverts an inline title or cancels an edit, or closes a modal/dialog (which also traps `Tab`); `E` opens a doc for editing, and inside it `⌘/Ctrl-S` saves immediately. In the rich editor: `⌘/Ctrl-B` bold, `⌘/Ctrl-I` italic, `⌘/Ctrl-Shift-S` strikethrough, `⌘/Ctrl-E` code, `⌘/Ctrl-K` link (on a selection or in a link), `/` the block menu (keys as in the @ menu); in either mode `⌘/Ctrl-Shift-A` attaches files. A capture-phase guard drops any keystroke from an IME composition before it reaches a shortcut.

## Documents

Linear-style docs inside teams. Markdown is the source of truth.

- **documents**: id, workspace, team_id, slug (`UNIQUE (workspace, slug)`), title, content, position, project_id (see Projects), created_at, updated_at, updated_by_id, deleted_at (see Trash).
- **document_versions**: id, document_id, title, content, author_id, created_at. A version is written on every title/content change. Autosave-friendly: if the latest version has the same author and was first saved < 10 min ago, overwrite its title and content instead of inserting. Its `created_at` stays the first save's time, so a long session still gets a new version every 10 minutes. The first version (creation) is never merged into, and a PATCH with `checkpoint: true` (the web's Restore) always gets its own version.
- **document_refs**: document_id, issue_id, ord. Recomputed on every content change from `\b[A-Z]{2,5}-\d+\b` matches that resolve to real issues in the doc's workspace, by their current identifier or one they had before a move (first-mention order).
- Slugs are unique within a workspace and stable (400 `A document's slug never changes`). The slug defaults to the title's, deduped (`-2`, `-3`…); an explicit bad one is 400 `Invalid slug "X": use a-z, 0-9 and single dashes, e.g. "api-design"`, a taken one 409 `Slug "x" is already taken`. A doc can move to another team of the same workspace (it keeps its project; it goes last there unless `position` is given, and the attachments in its content and comments move with it). It can be attached to one project of its workspace (`project`, a slug; another workspace's or an unknown one is 400 `Unknown project "x"`; `null` detaches it) while keeping its team. Deleting a doc moves it to the trash (see Trash).
- Search (`q`) matches title and content as a literal substring, like issue search.

## Projects

Linear's projects: a body of work toward a goal, in one workspace, spanning one or more of its teams, with a lead, a status, a target date, milestones (its stages), docs and progress. Unlike Linear: statuses are a fixed list, there's no lead team (`teams` is just the set taking part), a project can't be deleted (cancel it), and progress counts issues, not estimates. Initiatives, project updates, health and roadmaps are out of scope.

- **projects**: id, workspace, slug (unique within the workspace, stable like a doc's: `UNIQUE (workspace, slug)`; derived from the name, deduped, `project-<n>` if nothing Latin is left), name, description (markdown), status (`backlog` by default, `planned`, `in_progress`, `paused`, `completed`, `canceled`: `PROJECT_STATUSES`), lead_id (a person, an active member), target_date (`YYYY-MM-DD`, a real date, else 400 `targetDate must be a date like 2026-09-30`), creator_id, created_at, updated_at (bumped strictly forward on every change: the version token for `baseUpdatedAt`).
- **project_teams**: project_id (cascades), team_id; primary key (project_id, team_id). At least one; each a team of the project's workspace (a key resolves only there, so another workspace's is 400 `Unknown team "X"`). An issue joining the project (created, set, or moved to another team) adds its team. `teams` in a PATCH replaces the teams you see (ones you don't see stay), but a team with issues in the project (trashed ones too) stays: 409 `3 WEB issues are in this project`.
- **milestones**: id, project_id (cascades), name (unique in the project, case-insensitively: 409), description, target_date, position (ordering; new ones go last), created_at. Renaming one bumps and publishes its issues (no history row); deleting one takes it off its issues (trashed ones too), each logging a `milestone` change.
- **Issues**: `project` (a slug of the issue's workspace, else 400 `Unknown project "x"`) and `milestone` (a name in the issue's project after the change, case-insensitively: 400 `Unknown milestone "x" in <slug>`, or 400 `Set a project first: a milestone is a stage of one` without one). An issue is in at most one project and one of its milestones. A different project clears the milestone unless the same change names one of the new project's; `project: null` clears both. A new issue with a `parent` and no `project` joins its parent's project and milestone; `project: null` opts out. Joining or leaving bumps only the issue (history `project`/`milestone`, webhook `updatedFrom`) and publishes the issue and the projects it left and joined.
- **Progress** (`progress`, 0–1) over live issues (not trashed; archived ones count): a completed-category issue counts 1, a started-category one ½, canceled-category ones drop out: `(completed + ½ started) / (issues − canceled)`, or 0 when that's 0. `issueCount` counts live issues. The same for each milestone over its issues.
- Everything is in the request's workspace: another workspace's project is 404 and never listed. Any member, person or agent, creates and changes projects and milestones (a read key can't). Every change publishes `changed("project", slug)`; milestone changes don't bump the project's `updated_at` (its description's version), like doc comments.

## Attachments

Linear's uploads: files (screenshots, logs, reports) attached to a workspace and linked from any markdown (descriptions, comments, docs). Unlike Linear's, they're private to the workspace (served only to its signed-in members), 10 MB each (`MAX_UPLOAD_BYTES`), and only raster images display inline.

- **Storage** (`attachments.ts` `files`): on Bun `attachments/<id>` in the database's folder (`local.ts`, `paths.ts` `attachmentsDir()`; `/app/data/attachments` in Docker), created at startup; on Workers the R2 object `<id>` (bucket `docket-attachments`, binding `ATTACHMENTS`). `id` is 16 random bytes, base64url (22 characters): the row's key and the file's name. The upload streams straight into storage, never held whole (on disk to `<id>.part`, then renamed, so it's whole or absent; to R2 at its Content-Length), then its type is sniffed from the stored file's first 8 KB and its row inserted; an empty or oversized file, or a failed insert, removes the file, so no row points at missing bytes. Files never change. No delete or cleanup yet: an attachment stays after the text linking it is edited or deleted.
- **attachments**: id, workspace (cascades), team_id (the team it was uploaded in, or moved to with its issue or doc; null: the workspace's), name, content_type, size, uploader_id, created_at. `Attachment` in the API: `{ id, url, name, contentType, size, uploader, team, createdAt }`, `url` = `/api/attachments/<id>/<name>` (the name percent-encoded, parentheses too, so it can't end a markdown link).
- **Name**: the uploaded name without `/`, `\`, `"`, control characters or bidi overrides, trimmed, at most 200 characters; empty is `file`.
- **Type**: sniffed from the first bytes, never the client's claim: PNG, JPEG, GIF, WebP (`RIFF….WEBP`) as their image type; `%PDF-` as `application/pdf`; valid UTF-8 without a NUL in the first 8 KB as `text/plain; charset=utf-8`; anything else `application/octet-stream`. So SVG and HTML are text, never rendered.
- **Serving**: only an active member of the file's workspace gets it (a key: only its own workspace), and for a file uploaded in a team only those who see the team (a private team's: its members; see Teams and guests), 404 otherwise (also for a row whose file is missing), 401 signed out. The id is matched against `^[A-Za-z0-9_-]{22}$` and looked up; a path is never built from the URL. The name in the URL is cosmetic. Headers: the stored `Content-Type`; `Content-Disposition: inline` for the four image types, else `attachment`, with `filename="<ASCII fallback>"; filename*=UTF-8''<encoded>`; `Cross-Origin-Resource-Policy: same-origin`; `Cache-Control: private, max-age=31536000, immutable`; plus the usual headers (nosniff, CSP, no framing).
- Uploading notifies no one, logs no activity and sends no webhook event; the text that links a file does, as usual.

## Deploy

The server serves the web app at `/`, `/login`, `/setup`, `/:ws` and `/:ws/*`, and at the paths from before URLs carried the workspace (`/settings/*`, `/t/*`, `/issue/*`, `/docs`, `/doc/*`) so the app can redirect them; `/api/*` and known files win over `/:ws`, and unknown `/icons/*` stay plain 404s.

`Dockerfile` (oven/bun image) + `docker-compose.yml`: volume `./data:/app/data` (the database, `attachments/` and `backups/`), port published on `127.0.0.1` only. HTTPS and exposure are the operator's choice: a hostname other than `localhost`, `127.0.0.1` or `[::1]` must be in `DOCKET_HOSTS` (see Rules for every request). Setup code, `sign-in-link` and the env vars: see README.

**Cloudflare Workers** (`wrangler.jsonc`), on the free plan (10 ms of CPU a request): the web app is static assets (`scripts/build-worker.ts` builds `dist/` with a `_headers` file from `secure()`; SPA fallback). `/api/*`, `/mcp`, `/ws` and `/icons/*` run the Worker first: an icon is served from the assets and anything else under `/icons` is a plain 404; the rest goes, without the client's `x-forwarded-*` headers, and with its body read whole except an upload's, which streams through to R2 (the object reads every one to the end, even one it refuses), to one SQLite-backed Durable Object (`Docket`) serving `app.ts`'s routes: its storage through `durableStore` (no booleans or bigints in its SQL, nested transactions are savepoints), attachment bytes in R2, the client IP from `CF-Connecting-IP`. WebSockets hibernate; each keeps its topics in its attachment (a socket takes at most 10 tags), and a publish goes through them all. Background work: an hourly cron (at :00, so a cycle ends within a minute of midnight UTC) runs the housekeeping Bun does at startup and on its timers (trash purge, auto-archive, cycles, the delivery log, due deliveries); the alarm is set only for a queued webhook delivery or retry; a kick runs in `waitUntil`. Webhook targets: a literal IP is checked, hostnames aren't looked up (no DNS on Workers; `localhost` names are refused). Vars and secrets are the same env names (`DOCKET_URL`, `DOCKET_HOSTS`); `DOCKET_SETUP_CODE` is required for setup there (503 without it), since a random one would change whenever the object wakes. `ADMIN_TOKEN`, set only while needed, turns on the operator endpoints in `worker.ts` (the import, and `sign-in-link`: `ADMIN_TOKEN=… DOCKET_URL=https://… bun run sign-in-link <username> [workspace]`).

**Import** (`ADMIN_TOKEN=… bun scripts/import.ts <url> <snapshot.db> [attachments dir]`), in small requests that can be repeated: rows go table by table, parents first (and a table's rows after those they reference in it), about 64 KB per request, inserted as they are with `INSERT OR IGNORE`; a table whose count already matches is skipped. Files go one a request, streamed, each only if R2 doesn't already hold it with the same SHA-256; R2 checks the bytes against the SHA-256 sent with them. Then the check: every table page by page (100 rows: count and SHA-256 of typed values in value order), each table's `foreign_key_check`, `quick_check`, the schema's hash without comments, and every attachment's R2 object with its SHA-256. It exits non-zero unless everything matches; run it again to resume. Delete `ADMIN_TOKEN` afterwards.

**Backup** (`BACKUP_TOKEN=… bun scripts/backup.ts <url> <dir>`, nightly from the operator's machine): the `BACKUP_TOKEN` secret turns on read-only `GET /api/backup/*` (tables and schema version; a table's rows by rowid, about 256 KB a request; attachment ids with their R2 size and MD5; one attachment's bytes), and nothing else. It writes `<dir>/docket-<UTC time>.db`, a SQLite file with this checkout's schema (which must be at the Worker's version) that `import.ts` restores and `bun:sqlite` opens, failing unless `integrity_check` and `foreign_key_check` pass (pages are read while Docket runs, so a write in between can break that: run it again); mirrors into `<dir>/attachments` only files missing or different by MD5, each checked once written; and keeps its newest 14 snapshots, never touching other files.
